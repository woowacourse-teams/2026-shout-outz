# ADR-001. Dropit 주 데이터베이스 선택

- 작성일: 2026-08-05
- 상태: Accepted
- 최종 결정: PostgreSQL
- 결정 범위: 프로토타입 구현과 무관한 신규 설계

## 1. 최종 결정

Dropit의 주 데이터베이스로 PostgreSQL을 채택한다.

내가 이 서비스의 데이터베이스 선택을 책임지는 상황이라면 PostgreSQL로 바로 결정하고, MySQL을 추가 비교하는 작업은 여기서 끝낸다.

이 결정은 PostgreSQL이 모든 상황에서 MySQL보다 빠르다는 뜻이 아니다. MySQL도 이 서비스의 1차 기능을 충분히 구현할 수 있다. 다만 Dropit은 단순 CRUD 서비스가 아니라 다음 데이터를 계속 조합해야 하는 서비스다.

- 서비스 목록과 상세 정보
- 카테고리·기술 태그
- 제작자와 서비스 관계
- 사용자별 좋아요·북마크
- 댓글·답글
- 인기순·최신순·추천·통계
- 인증·소유권·삭제·복구·운영 상태

이 도메인에서는 초기 CRUD보다 시간이 지날수록 조회 조건, 집계, 랭킹 규칙, 운영 쿼리가 복잡해질 가능성이 높다. PostgreSQL은 관계형 무결성을 유지하면서 복잡한 SQL, JSON 메타데이터, 전문 검색, 부분·표현식 인덱스 등으로 확장할 여지가 더 크다.

반대로 MySQL을 선택해야 할 팀 표준, 운영 인력, 비용상의 결정적 근거는 현재 주어지지 않았다. 따라서 제품 요구사항만 놓고 내려야 하는 기본 결정은 PostgreSQL이다.

## 2. 판단에서 제외한 것

다음 내용은 이번 결정의 근거로 사용하지 않았다.

- 현재 Supabase 사용 여부
- 현재 데이터가 존재하는지 여부
- 현재 테이블과 컬럼 구조
- 현재 Spring/JPA 코드와 의존성
- 현재 테스트 DB와 배포 환경
- 기존 데이터 이전 비용

서비스를 처음부터 새로 설계하고, PostgreSQL과 MySQL을 동일한 출발선에서 비교했다.

## 3. 서비스 요구사항을 데이터 요구사항으로 변환

기능 요구사항은 다음과 같은 데이터베이스 요구사항으로 바뀐다.

| 서비스 요구사항 | 데이터베이스 요구사항 |
|---|---|
| 공개 서비스 탐색 | 조건 필터, 정렬, 페이지네이션, 검색, 인덱스 |
| 여러 카테고리·기술 태그 | 다대다 관계, 중복 방지, 태그별 집계 |
| 제작자별 서비스 관리 | 사용자·프로필·서비스의 관계와 소유권 제약 |
| 좋아요·북마크 | 사용자-서비스 복합 유일성, 멱등 처리, 동시성 제어 |
| 댓글·답글 | 자기 참조 관계, 부모 댓글 검증, 정렬·삭제 정책 |
| 크루 인증과 역할 | 권한 상태, 접근 제어, 권한 변경 이력 |
| 인기순·추천·방문 통계 | 이벤트 또는 원천 관계 보존, 집계, 기간별 분석 |
| 삭제·복구·운영 관리 | 명시적인 상태 모델, 보존·감사 정책 |
| 향후 신고·알림·큐레이션 | 기존 핵심 모델을 깨지 않는 확장성 |

핵심은 “어떤 DB가 게시글을 저장할 수 있는가”가 아니다. 두 DB 모두 가능하다. 핵심은 관계가 늘어나고 조회 조건이 복잡해져도 데이터 무결성과 쿼리 변경을 함께 관리할 수 있는가다.

## 4. 신규 데이터 모델 원칙

DB를 PostgreSQL로 선택하더라도 PostgreSQL 특화 기능에 처음부터 과도하게 의존하지 않는다.

### 4.1 조회·정렬 대상은 정규화한다

카테고리와 기술 태그는 배열이나 JSON 한 컬럼에 넣지 않고 관계 테이블로 설계한다.

```text
users ── makers
  │
  ├── apps ── app_categories ── categories
  │    └── app_tags ── tags
  │
  ├── app_likes ── apps
  ├── app_bookmarks ── apps
  └── comments ── apps
```

이 구조는 카테고리·태그 이름 변경, 중복 방지, 사용량 집계, 여러 조건의 조합 검색에 유리하다. 데이터베이스를 바꾸더라도 유지할 수 있는 표준적인 모델이다.

### 4.2 JSON은 확장 데이터에만 사용한다

외부 서비스의 원본 메타데이터, 추천 실험용 속성처럼 구조가 자주 바뀌는 값은 JSON으로 저장할 수 있다. 반면 필터·정렬·권한·무결성에 사용하는 값은 일반 컬럼과 관계 테이블로 둔다.

PostgreSQL에서는 이런 확장 영역에 `jsonb`와 관련 인덱스를 사용할 수 있다. MySQL도 JSON을 지원하지만, 이번 결정은 JSON 하나만으로 결정한 것이 아니라 관계형 질의와 운영 확장성을 함께 본 결과다.

### 4.3 상호작용은 트랜잭션으로 보호한다

좋아요·북마크·댓글·조회수는 다음 규칙을 데이터베이스와 애플리케이션 양쪽에서 보호한다.

- `(user_id, app_id)` 복합 PK 또는 UNIQUE로 중복 방지
- 상태 변경과 카운터 변경을 하나의 트랜잭션으로 처리
- 삭제·복구 시 공개 목록과 개인 목록의 노출 규칙을 일관되게 처리
- 카운터 외에 원천 관계 또는 이벤트를 보존해 재집계 가능하게 구성

## 5. PostgreSQL과 MySQL 비교

### 5.1 필수 기능

| 항목 | PostgreSQL | MySQL | 결론 |
|---|---|---|---|
| 관계형 모델 | PK, FK, UNIQUE, CHECK, 조인, 집계 지원 | InnoDB 기준으로 동일한 핵심 기능 지원 | 동점 |
| 트랜잭션·동시성 | MVCC, 격리 수준, 행 잠금, 다양한 제약 기능 | InnoDB가 ACID, 행 잠금, 일관된 읽기 지원 | 동점 |
| 좋아요·북마크 | 복합 유일성과 원자적 갱신 구현 가능 | 복합 유일성과 원자적 갱신 구현 가능 | 동점 |
| 댓글·답글 | 자기 참조 FK와 트랜잭션 검증 가능 | 자기 참조 FK와 트랜잭션 검증 가능 | 동점 |
| 기본 검색 | 전문 검색, 랭킹, 사전, 인덱스 확장 가능 | InnoDB FULLTEXT와 자연어·불리언 검색 제공 | 동점 |
| JSON 메타데이터 | `jsonb` 연산·포함 검색·인덱싱 선택지가 넓음 | JSON 타입과 JSON 검색·수정 함수 제공 | PostgreSQL 우세 |

필수 기능만 보면 두 DB 모두 합격이다. 따라서 “MySQL로도 되나?”에 대한 답은 “된다”이다. 하지만 이번 질문은 가능한 DB가 아니라 책임지고 하나를 정하는 문제이므로, 차이는 확장성 기준에서 판단한다.

### 5.2 확장성과 운영

| 판단 기준 | PostgreSQL | MySQL | 평가 |
|---|---|---|---|
| 탐색·랭킹 쿼리 | 복잡한 조인·집계·윈도 함수·CTE·부분/표현식 인덱스를 활용하기 좋음 | 조인·집계·윈도 함수·CTE·인덱스로 구현 가능 | PostgreSQL 우세 |
| 활성 데이터 인덱싱 | 상태 조건을 포함한 부분 인덱스로 공개 목록 쿼리를 최적화하기 좋음 | 복합 인덱스나 생성 컬럼 등으로 구현 | PostgreSQL 우세 |
| 유연한 메타데이터 | `jsonb`와 GIN 계열 인덱스 등 선택지가 있음 | JSON 인덱싱과 함수 인덱스로 구현 | PostgreSQL 우세 |
| 분석·통계 확장 | 복잡한 SQL과 확장 기능을 한 DB에서 시도할 여지가 큼 | 가능하지만 분석 요구가 커지면 별도 구조를 고려할 가능성이 큼 | PostgreSQL 우세 |
| 단순 운영 | 기능이 많은 만큼 설계 선택지가 많음 | 단순 CRUD 서비스로 시작하기 쉬움 | MySQL 우세 |
| 관리형 서비스 | 주요 클라우드에서 사용 가능 | 주요 클라우드에서 사용 가능 | 동점. 조직 표준이 결정 |

MySQL의 단순 운영상 장점은 인정한다. 하지만 이 프로젝트에서 운영 표준이나 팀 역량이 MySQL을 강제하지 않는 한, 단순함만으로 확장성의 선택지를 포기할 이유는 없다.

## 6. 결정 매트릭스

점수는 성능 벤치마크가 아니라 신규 제품 설계 적합도다. 1점은 불리하고 5점은 유리하다는 의미다.

| 기준 | 비중 | PostgreSQL | MySQL | 판단 근거 |
|---|---:|---:|---:|---|
| 관계형 무결성 | 25 | 5 | 5 | 두 DB 모두 충족 |
| 트랜잭션·동시성 | 20 | 5 | 5 | 두 DB 모두 충족 |
| 탐색·랭킹·통계 확장 | 25 | 5 | 4 | PostgreSQL이 복잡한 조회와 인덱스 선택지를 더 넓게 제공 |
| 유연한 메타데이터 | 15 | 5 | 4 | PostgreSQL `jsonb`의 연산·인덱싱 선택지가 더 넓음 |
| 검색 확장 경로 | 5 | 4 | 4 | 두 DB 모두 기본 검색 제공. 고도화 시 외부 검색 시스템 검토 |
| 운영·관리형 서비스 | 10 | 4 | 4 | 조직 제약이 없으므로 동점 |
| 가중 합계 | 100 | **4.8 / 5** | **4.4 / 5** | PostgreSQL 선택 |

점수 차이는 압도적이지 않다. 그럼에도 PostgreSQL을 고르는 이유는 필수 기능이 아니라, 서비스가 성장했을 때 데이터베이스를 다시 바꾸지 않고 해결할 수 있는 문제의 범위가 더 넓기 때문이다.

## 7. MySQL을 탈락시킨 이유

MySQL은 기술적으로 탈락한 것이 아니다. 다음과 같은 상황이면 MySQL을 선택할 수 있다.

- 회사가 MySQL을 표준으로 정하고 운영 자동화·모니터링·장애 대응 체계를 갖고 있음
- 팀의 MySQL 운영 경험이 PostgreSQL보다 압도적으로 높음
- 제품을 장기간 단순 CRUD와 목록 조회 범위로 제한함
- 검색·랭킹·통계를 별도 시스템으로 분리하기로 이미 결정함
- MySQL 관리형 서비스의 비용 또는 지원 조건이 정량적으로 더 유리함

현재는 위와 같은 MySQL 고유의 결정적 이점이 없다. 따라서 MySQL을 선택할 이유보다 PostgreSQL을 선택했을 때 남는 확장 선택지가 더 크다.

## 8. PostgreSQL 도입 시 지킬 원칙

PostgreSQL을 선택했다고 해서 모든 문제를 PostgreSQL의 특수 기능으로 해결하지 않는다.

1. 핵심 모델은 표준 관계형 테이블과 제약 조건으로 설계한다.
2. 카테고리·태그·좋아요·북마크는 관계 테이블과 복합 유일성으로 표현한다.
3. JSONB는 구조가 자주 바뀌는 부가 데이터에만 사용한다.
4. 서비스 목록·검색·랭킹 쿼리는 대표 데이터로 실행 계획을 확인한 뒤 인덱스를 추가한다.
5. 한국어 형태소·오타·자동완성이 중요해지면 DB 검색 기능만 고집하지 않고 검색 시스템을 분리한다.
6. 카운터는 원천 관계/이벤트와 정합성을 검증할 수 있게 설계한다.
7. DB 특화 SQL을 도입할 때는 도입 이유와 표준 SQL 대안을 의사결정 기록에 남긴다.

## 9. 재검토 조건

다음 조건이 실제로 발생할 때만 결정을 다시 연다.

- 회사·클라우드의 DB 표준이 MySQL로 확정됨
- 팀의 PostgreSQL 운영 역량이 제품 리스크로 확인됨
- 대표 쿼리 부하 테스트에서 PostgreSQL이 목표 성능이나 비용을 충족하지 못함
- 여러 DB 엔진을 동시에 지원해야 하는 제품 요구사항이 생김

그 전까지는 PostgreSQL을 기준으로 스키마, API, 테스트, 운영 자동화를 설계한다.
