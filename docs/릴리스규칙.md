# 릴리스 규칙

배포 이후 문제가 생겼을 때 어느 배포에서 무엇이 바뀌었는지 확인할 수 있도록, production 배포마다 버전을 붙인다.

---

## 릴리스 단위

**develop → main 머지 한 번이 릴리스 하나다.** main에 머지되면 production에 배포되기 때문이다.

프론트엔드와 백엔드는 버전을 나누지 않는다. 사용자에게는 둘이 하나의 서비스로 제공되므로 서비스 전체에 버전 하나를 붙인다.

버전은 Git 태그로만 관리한다. `frontend/package.json`과 `backend/build.gradle`의 version 값은 릴리스 버전과 관계없다.

---

## 버전 결정

버전은 `vMAJOR.MINOR.PATCH` 형식이며 첫 릴리스는 `v0.1.0`이다.

**develop → main PR 제목의 `[파트/작업 종류]` 태그**로 다음 버전을 정한다. 파트는 FE와 BE를 함께 내보내므로 `ALL`을 쓴다.

| develop → main PR 제목 | 올리는 자리 | 최신 태그가 `v1.2.3`일 때 |
| --- | --- | --- |
| 작업 종류 뒤에 `!` | MAJOR | `[ALL/feat!] ...` → `v2.0.0` |
| `feat`, `feature` | MINOR | `[ALL/feat] ...` → `v1.3.0` |
| 그 외 모든 작업 종류 | PATCH | `[ALL/fix] ...` → `v1.2.4` |

- 작업 종류는 이번 릴리스에 포함된 PR 중 **가장 높은 등급**으로 고른다. PR의 **Commits** 탭에서 목록을 확인한다.
  ```
  이번에 나가는 PR
    [BE/feat] 이미지 처리 상태 조회 API 추가 (#275)   → MINOR
    [FE/fix] 관리자 프로젝트 승인 화면 보완 (#265)    → PATCH

  가장 높은 등급은 MINOR → [ALL/feat] ...
  ```
- `!`는 기존 방식과 호환되지 않는 변경에 붙인다. 기존 URL을 더 이상 쓸 수 없게 되거나, 사용자가 기능을 쓰는 방식이 크게 달라지는 경우가 해당한다.
- refactor, chore, infra처럼 사용자에게 보이지 않는 변경만 있어도 PATCH를 올린다. production에 배포되는 이상 되돌아갈 기준이 필요하다.
- 0.x에서도 `!`가 있으면 MAJOR를 올린다. `v0.3.0`에서 `[ALL/feat!] ...`를 머지하면 `v1.0.0`이 된다.
- 첫 릴리스는 저장소에 `v*` Git 태그가 아직 없으므로, 제목의 작업 종류와 관계없이 `v0.1.0`이 된다.

---

## 릴리스 절차

1. develop → main PR을 만든다.
2. **Commits** 탭에서 이번에 나가는 PR 목록을 보고 작업 종류를 정해 제목을 쓴다. 본문에는 변경 목록을 적는다.
   ```
   [ALL/feat] 피드 OG 태그 정보, 이미지 처리 상태 조회 (#290)
   ```
3. **Create a merge commit**으로 머지한다. squash로 머지하면 main과 develop의 이력이 이어지지 않아 다음 릴리스의 변경 목록이 섞인다.
4. 머지되면 `Create Release Tag` 워크플로우(`.github/workflows/release-tag.yml`)가 최신 태그와 제목의 작업 종류로 버전을 계산해, 머지 커밋에 태그와 GitHub Release를 만든다. 릴리스 노트는 GitHub가 PR 목록으로 자동 생성한다.

### 태그가 만들어지지 않았을 때

PR 제목에 `[파트/작업 종류]` 태그가 없으면 워크플로우가 실패한다. 이미 머지된 뒤이므로 Actions 로그에서 원인을 확인하고 직접 태그를 만든다. main 브랜치에 push할 권한이 없어도 된다.

```bash
gh release create v0.2.0 --target main --generate-notes
```

`gh`가 없으면 GitHub 저장소의 **Releases → Draft a new release**에서 태그에 `v0.2.0`, Target에 `main`을 고르고 **Generate release notes**를 누른 뒤 게시한다.

어느 방법이든 target은 원격 main의 최신 커밋이다. 그사이 main에 다른 머지가 있었다면 `main` 대신 릴리스 머지 커밋의 SHA를 넣는다.

---

## 되돌리기

태그로 문제가 생긴 배포와 직전 정상 버전을 찾고, 두 버전 사이의 변경을 확인한다.

```bash
git log --first-parent --format='%h %s' v0.1.0..v0.2.0^2
```

> 현재 배포 워크플로우(`frontend-deploy.yml`, `backend-deploy-branch.yml`)는 `main`과 `develop` 브랜치에서만 동작한다. 태그를 골라 바로 재배포하는 기능은 아직 없다.

---

## 이후 자동화

변경 목록 확인과 버전 계산까지 자동화하고 싶어지면 [Release Please](https://github.com/googleapis/release-please) 도입을 검토한다. 이 도구는 `feat(frontend): ...` 같은 Conventional Commits 형식만 읽으므로, 그때는 PR 제목 형식을 바꿔야 한다.
