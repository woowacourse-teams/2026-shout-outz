# ADR-002: 운영 데이터베이스를 PostgreSQL로 이전

### 결정일 및 결정자
- 결정일: 2026.08.19
- 결정자: 조상준(샤를), 최재영(재키), 박다혜(라이)
- 작성자: 박다혜(라이)

## 상태 (Status)

- 수락됨(Accepted)

## 컨텍스트 (Context)

Dropit은 현재 Supabase의 PostgreSQL 스토리지를 기본 저장소로 사용하며, Supabase가 제공하는 Github OAuth 인증, RLS 기반 접근 제어, 자동 생성 API를 사용하여 프로토타입을 운영 중이다.

DB는 서버를 배포하는 시점에 옮기는 것이 비용 측면에서 부담이 적기 때문에,  이 문서에서는 해당 사안에 대한 내용을 정리해 본다.

운영 환경에서의 DB의 조건은 다음과 같다.

- **복구 목표를 우리가 정의할 수 있어야 한다.**

백업 주기와 보관 기간이 요금제에 종속된다. 허용 가능한 데이터 손실 범위와 복구 소요 시간, 시점 복구 가능 여부를 서비스 요구사항에 맞춰 설정할 수 없다.

- **우리 통제 밖의 사유로 중단되지 않아야 한다.**

Supabase 무료 스토리지 사이즈인 5GB를 사용하다가, 공간이 초과되어 갑작스럽게 임시 방편으로 플랜 업그레이드를 하게 되었다. 이와 같이, 우리 통제 밖의 사유로 DB 사용이 중단되는 것이 현재 구조의 한계다.

플랫폼을 벗어나면서 스키마를 새로 설계하므로, 엔진을 바꾸는 비용은 이 시점에 가장 낮다. 그럼에도 **PostgreSQL**을 유지하기로 한 근거는 두 가지다.

- 목록 조회는 카테고리 필터, 기술 태그, 검색어, 인기순·최신순 정렬이 임의로 조합되며, 소프트 삭제 구조상 삭제되지 않은 행을 거르는 조건이 거의 모든 조회에 붙는다. 조건 조합이 사전에 고정되지 않아 모든 경우에 복합 인덱스를 두는 방식은 성립하지 않고, 특정 조건에만 인덱스를 만드는 부분 인덱스와 여러 인덱스를 결합하는 비트맵 스캔이 필요하다. 둘 다 PostgreSQL에서 사용할 수 있으나 MySQL에는 없거나 제한적이다.
- 프로토타입 단계에서 쌓인 데이터는 이미 PostgreSQL에 있다. 엔진이 같으면 스키마가 바뀌어도 변환을 SQL 안에서 처리할 수 있지만, 엔진을 바꾸면 별도의 이전 파이프라인을 만들어야 하고, 이전 비용이 더 커진다.

위의 조건과 더불어, 데이터베이스 관리 서비스를 선택했던 결정적인 기준은 **비용 제약**이다. 우리 팀은 현재 프로젝트 기간 동안 우아한테크코스로부터 AWS 사용 비용을 지원받으므로, AWS 안에서 운영하면 지원 기간 동안 인프라 비용이 발생하지 않는 반면, 외부 서비스의 유료 등급은 전액 팀 부담이 된다. 비용 제약을 고려했을 때, AWS를 선택하는 것이 현실적인 방안이 될 수 있다.

## 결정 (Decision)

데이터베이스 엔진을 PostgreSQL로 유지한 채, Supabase에서 제공하던 인증, 인가, 데이터 접근 계층에 대한 의존을 제거하고, 데이터베이스를 우리가 운영 파라미터를 통제하는 독립된 인스턴스로 분리한다. 이전 대상은 **Amazon RDS for PostgreSQL**로 한다.

애플리케이션 서버는 처음부터 새 데이터베이스에 접속한다. 현재 스키마는 프로토타입 단계에서 빠르게 작성되어, 테이블명이나 컬럼명이 논의된 서비스 정책과 어긋나는 부분이 많다. 따라서 스키마를 새로 설계한 다음, 데이터 이전 작업을 거쳐 전환한다.

## 결과 (Consequences)

**긍정적 영향**

- 백업 주기, 보관 기간, 시점 복구 범위, 엔진 버전, 인덱스와 커넥션 설정을 직접 정한다.
- 지원 기간 동안 인프라 비용이 발생하지 않는다.
- 엔진이 동일하므로 타입 표현을 매핑할 필요가 없고, 스키마 변환을 SQL 안에서 처리할 수 있다.

**부정적 영향**

- AWS 인프라 구성이 새로 필요하다.
- AWS 비용 지원이 종료되면 인프라 비용을 팀이 부담해야 한다.
- 이전 범위가 데이터베이스에 그치지 않는다. 이미지 파일과 인증, 인가 역시 따로 옮겨야 하는 대상이다.

**중립적 영향**

- 새 스키마 설계 시 결정할 사항: 카테고리와 기술 태그의 표현 방식(배열 또는 조인 테이블), 서비스 식별자 타입, 좋아요 및 실행 수 비정규화 카운터의 유지 여부
- 방문자 통계처럼 일자 기준으로 집계하는 기능이 `Asia/Seoul`을 기준으로 하므로, DB와 서버의 타임존 처리를 명시적으로 통일해야 한다.

## 검토한 대안 (Options Considered)

**운영 형태**

**대안1: Supabase 플랫폼 유지 + 애플리케이션 서버에서 접속**

이전 비용이 없고 Flyway 도입도 가능해 가장 저렴하다. 그러나 컨텍스트 2, 3번이 해소되지 않고 `auth.users` 결합이 유지되어 이전 비용이 계속 상승한다. 운영 통제권 확보라는 목표에 비추어 선택하지 않았다.

**대안2: Supabase 유료 등급으로 상향**

일시 정지 리스크가 해소되고 백업 옵션이 개선된다. 그러나 복구 목표를 우리가 정의하는 것이 아니라 제공되는 범위에서 선택하게 되고, 플랫폼 종속이 그대로 남는다. 결정적으로 팀이 지원받는 비용은 AWS에 한정되므로 이 대안의 요금은 전액 자비 부담이 된다. 통제권과 비용 양쪽에서 불리해 선택하지 않았다.

**대안3: EC2에 PostgreSQL을 직접 설치해 운영**

비용 지원 범위 안에 있고 설정 자유도가 가장 높다. 그러나 백업, 패치, 장애 대응까지 전부 팀이 부담하게 된다. 복구 목표와 파라미터를 직접 정하는 것을 고려했을 때, 관리형 서비스로 충분하다고 판단해 선택하지 않았다.

**데이터베이스 엔진**

**대안: MySQL 등 다른 엔진으로 전환**

이전 작업을 어차피 수행하므로 엔진을 함께 바꿀 수 있다. 그러나 배열·jsonb·timestamptz·plpgsql에 대한 의존 때문에 스키마 재설계와 데이터 변환 규칙 정의가 필요해 이전 비용이 크게 늘어난다. 또한 조건 조합이 예측되지 않는 목록 조회에 필요한 부분 인덱스와 배열 인덱스를 사용할 수 없다. 엔진 변경으로 얻을 이점이 확인되지 않아 선택하지 않았다.
