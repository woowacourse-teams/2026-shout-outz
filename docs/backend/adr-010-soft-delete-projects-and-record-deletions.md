# ADR 010: 프로젝트를 Soft Delete하고 삭제 이력을 별도로 기록한다

## 상태 (Status)

수락됨 (Accepted)

대체된 경우: 해당 없음

## 컨텍스트 (Context)

사용자가 프로젝트를 삭제해도 일정 기간 동안 복구할 수 있어야 한다. 운영자는 프로젝트의 삭제, 복구, 관리자 조치, 시스템에 의한 영구 삭제를 추적할 수 있어야 한다.

`projects`의 현재 상태만 관리하면 동일한 프로젝트가 여러 번 삭제되고 복구된 이력을 남기기 어렵다. 반대로 삭제할 때마다 프로젝트 본문을 즉시 제거하면 사용자 복구 기능을 제공할 수 없다.

## 결정 (Decision)

프로젝트의 현재 삭제 상태는 `projects.deleted_at`으로 표시하고, 삭제 행위마다 `project_deletions`에 이력 행을 추가한다.

사용자가 프로젝트를 삭제하면 `projects.deleted_at`을 기록하고 `project_deletions`에 삭제 주체, 삭제 유형, 삭제 시각, 복구 기한을 저장한다. 사용자가 복구 기한 안에 복구하면 `projects.deleted_at`을 `NULL`로 되돌리고 해당 삭제 이력에 복구 주체와 복구 시각을 기록한다. 복구할 때는 새로운 삭제 이력을 추가하지 않는다.

프로젝트를 다시 삭제하면 새로운 삭제 이력을 추가한다. 복구 기한이 지난 프로젝트의 복구 요청은 애플리케이션이 거절한다. 복구 기한이 지나 시스템이 영구 삭제를 수행할 때도 시스템 작업을 나타내는 별도의 삭제 유형으로 이력을 남긴다.

## 결과 (Consequences)

**긍정적 영향**: 사용자가 삭제한 프로젝트를 복구할 수 있다. 프로젝트의 전체 삭제·복구 생명주기를 관리자 관점에서 추적할 수 있다. 반복된 삭제와 복구를 각각의 사건으로 기록할 수 있고, 사용자 삭제와 관리자 조치 및 시스템 작업을 구분할 수 있다.

**부정적 영향**: 프로젝트 상태와 삭제 이력을 함께 변경해야 하므로 삭제·복구 작업을 트랜잭션으로 처리해야 한다. 삭제 이력이 계속 쌓이므로 보관 및 정리 정책이 필요하다. 복구 기한 만료 프로젝트를 영구 삭제하는 배치와 외래키 관계를 별도로 운영해야 한다.

**중립적 영향**: 복구 가능 기간은 서비스 정책으로 관리하며, `projects`에 별도의 복구 가능 상태를 저장하지 않는다. 복구 가능 여부는 `deleted_at`과 `restore_deadline_at`을 기준으로 애플리케이션이 판단한다. 영구 삭제 시 삭제 이력을 보존하는 방법과 관련 외래키 처리 방식은 구현 단계에서 확정한다.

## 검토한 대안 (Options Considered)

**대안 1**: 프로젝트를 삭제할 때 즉시 Hard Delete한다. 구현은 단순하지만 사용자가 삭제한 프로젝트를 복구할 수 없고 삭제 생명주기와 운영 이력을 보존하기 어려우므로 선택하지 않았다.

**대안 2**: `projects.deleted_at`만 사용하고 별도의 삭제 이력 테이블을 두지 않는다. 현재 삭제 상태를 표현하기에는 충분하지만 반복된 삭제·복구와 삭제 주체 및 유형을 추적할 수 없으므로 선택하지 않았다.
