# ADR 006: 서비스 등록 권한을 승인 기록 테이블로 판단한다

## 상태 (Status)

수락됨 (Accepted)

## 컨텍스트 (Context)

Drop-it에서는 현재 크루 인증을 완료한 사용자에게 서비스 등록 권한을 제공한다. 하지만 서비스 등록 가능 여부를 `Users` 테이블의 `role` 값으로 판단하면 현재의 승인 정책인 “크루인가”가 데이터 모델에 직접 결합된다.

향후 서비스 등록 정책이 크루 여부에서 인증코드, 관리자 승인, 외부 사용자 대상 승인 등으로 변경될 수 있다. 이때 `Users.role`에 `CREW`를 저장하고 해당 값만 확인하는 구조는 기존 승인 정책과 새로운 승인 정책의 관계를 데이터베이스 변경으로 풀어야 하며, 기존에 승인된 사용자의 권한을 보존하기도 어렵다.

## 결정 (Decision)

서비스 등록 가능 여부는 사용자 유형이나 크루 여부가 아니라, 사용자 ID를 참조하는 별도의 승인 기록 테이블에 해당 사용자의 승인 정보가 존재하는지로 판단한다.

백엔드 서버는 서비스 등록 요청을 처리할 때 승인 기록 테이블을 조회한다. 해당 사용자 ID가 존재하면 서비스 등록을 허용하고, 존재하지 않으면 서비스 등록을 허용하지 않는다.

서비스 등록 권한 판단을 위해 `Users` 테이블에 크루 여부를 나타내는 역할 값을 필수로 저장하지 않는다. 크루 인증이나 인증코드와 같은 승인 방식은 승인 기록을 생성하는 정책으로 다루며, 서비스 등록 가능 여부를 판단하는 서버의 기준은 승인 기록의 존재 여부로 통일한다.

이 ADR은 승인 기록의 보존 기간, 철회 이력, 중복 승인 처리와 같은 기록 생명주기는 결정하지 않는다.

## 결과 (Consequences)

**긍정적 영향**: 현재의 “크루만 등록 가능” 정책을 사용자 기본 정보와 분리할 수 있다. 승인 기준이 크루 인증에서 다른 방식으로 변경되어도 서비스 등록 권한을 판단하는 데이터 구조를 그대로 유지할 수 있다. 서버는 서비스 등록 가능 여부를 승인 기록 테이블 하나를 조회해 일관되게 판단할 수 있다.

**부정적 영향**: 사용자 정보와 별도로 승인 기록을 관리해야 하며, 서비스 등록 요청마다 추가 조회가 발생한다. 승인 기록을 생성하거나 철회하는 관리 기능과 데이터 정합성 규칙을 별도로 설계해야 한다.

**중립적 영향**: 승인 기록 테이블의 정확한 스키마와 물리적 테이블명, 승인 철회 방식, 승인 이력 보존 방식은 후속 ADR에서 결정한다. 사용자 역할이 필요한 다른 기능이 생기는 경우에는 서비스 등록 권한과 분리해 별도의 역할 모델을 검토한다.

## 검토한 대안 (Options Considered)

**대안 1**: `Users` 테이블에 `role`을 저장하고 `CREW` 여부로 서비스 등록을 허용한다. 구현은 단순하지만 현재의 크루 정책이 서비스 등록 권한 모델에 직접 결합되고, 승인 정책이 변경될 때 사용자 데이터와 권한 판단 로직을 함께 변경해야 하므로 선택하지 않았다.

**대안 2**: 서비스 등록 요청이 발생할 때마다 크루 여부나 인증코드를 직접 확인한다. 요청 시점의 정책을 반영하기 쉽지만, 이미 승인된 사용자의 권한을 보존하기 어렵고 승인 결과를 별도로 추적할 수 없다. 승인 결과를 독립된 기록으로 관리하기 위해 선택하지 않았다.
