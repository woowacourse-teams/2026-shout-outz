# ADR-010: users와 user_profiles 테이블을 분리

### 결정일 및 결정자
- 결정일: 2026.08.19
- 결정자: 조상준(샤를), 최재영(재키), 박다혜(라이)
- 작성자: 최재영(재키)

## 상태 (Status)

수락됨 (Accepted)

## 컨텍스트 (Context)

사용자 정보에는 서로 다른 책임을 가진 데이터가 함께 존재한다.

계정 상태, 권한, 마지막 로그인 시각, 탈퇴 시각 등은 사용자를 식별하고 계정의 생명주기를 관리하기 위한 정보다. 반면 핸들, 표시 이름, 소속, 직무, 자기소개, 프로필 이미지는 서비스에서 사용자를 표현하기 위한 프로필 정보다.

이를 하나의 `users` 테이블에서 관리할 수도 있지만, 향후 계정 관리나 감사 기능이 확장될 경우 계정 관리 정보와 서비스 프로필 정보가 한 테이블에 계속 섞이게 된다. 프로필 필드가 늘어날수록 `users`의 책임 또한 함께 커진다.

반면 두 테이블을 분리하면 프로필을 표시하는 대부분의 조회에서 조인이 추가된다. 현재 서비스에서 닉네임과 프로필 이미지를 자주 사용한다는 점도 고려했지만, 1:1 관계의 조인 비용을 감수하고 책임을 명확히 분리하기로 했다.

## 결정 (Decision)

사용자 계정 관리 정보와 프로필 정보를 각각 `users`, `user_profiles` 테이블로 분리한다.

`users`는 사용자 식별과 계정의 상태, 권한, 로그인 및 생명주기를 관리한다.

`user_profiles`는 핸들, 표시 이름, 소속, 직무, 자기소개, 프로필 이미지 등 서비스에서 사용자를 표현하기 위한 정보를 관리한다.

`user_profiles.user_id`는 `users.id`를 참조하는 기본키이자 외래키로 사용하여 두 테이블의 1:1 관계를 표현한다.

## 결과 (Consequences)

**긍정적 영향**: 계정 관리와 서비스 프로필의 책임을 분리할 수 있다. 향후 계정 관리, 감사 기능이나 프로필 정보가 확장되더라도 각각의 테이블을 독립적으로 확장할 수 있다. `users`를 계정 관리에 필요한 정보 중심으로 유지할 수 있다.

**부정적 영향**: 사용자 이름이나 프로필 이미지가 필요한 조회에서 `user_profiles`와의 조인이 추가된다. 회원 생성 시 `users`와 `user_profiles`의 생성 정합성을 함께 보장해야 한다.

**중립적 영향**: 실제 조회 성능에 문제가 발생할 경우 캐싱이나 비정규화 등의 최적화를 조회 패턴을 확인한 뒤에 별도로 검토한다.

## 검토한 대안 (Options Considered)

**대안 1**: 계정 정보와 프로필 정보를 `users` 한 테이블에 저장한다. 조인이 없어 조회와 구현이 단순하지만, 공개 정보와 서버 전용 정보의 보안 경계가 약해지고 프로필 확장 시 계정 테이블의 책임이 커지므로 선택하지 않았다.

**대안 2**: 자주 사용하는 표시 이름과 프로필 이미지만 `users`에 두고 나머지 프로필 정보를 `user_profiles`로 분리한다. 사용자 목록이나 댓글 조회 시 일부 조인을 줄일 수 있지만, 하나의 프로필 책임이 두 테이블에 나뉘어 경계가 모호해지므로 선택하지 않았다.
