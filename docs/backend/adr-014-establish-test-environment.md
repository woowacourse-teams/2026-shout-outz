# ADR-014: 테스트 환경 구축

### 결정일 및 결정자
- 결정일: 2026.08.19
- 결정자: 조상준(샤를), 최재영(재키), 박다혜(라이)
- 작성자: 박다혜(라이)

## 상태 (Status)

- 수락됨(Accepted)

## 컨텍스트 (Context)

애플리케이션 테스트는 데이터베이스에 접근하는 범위를 포함한다. 이때 테스트가 운영과 다른 데이터베이스에서 실행되면, **특정 데이터베이스 고유의 문법이나 타입에 의존하는 코드가 테스트를 통과하고도 운영에서 실패한다.** 인메모리 데이터베이스의 호환 모드는 이 차이를 완전히 없애주지 못한다.

동시에 팀원마다 로컬에 설치된 데이터베이스의 버전과 설정이 다르면, 같은 테스트가 사람에 따라 다른 결과를 낸다. 테스트가 실패했을 때 코드 문제인지 환경 문제인지 구분할 수 없게 된다.

따라서 테스트 환경에는 두 가지 조건이 필요하다.

1. 운영과 동일한 데이터베이스 엔진으로 테스트한다.
2. 팀원 전원이 동일한 버전과 설정의 데이터베이스를 사용한다.

컨테이너는 두 조건을 함께 만족한다. 이미지에 엔진 버전과 초기 설정을 고정해 둘 수 있고, 가상 머신보다 가볍고 기동이 빨라 개발 중에 부담이 적다. 서버를 늘리거나 옮길 때도 같은 이미지로 동일한 환경을 재현할 수 있다.

## 결정 (Decision)

우리는 Docker Compose로 로컬에 PostgreSQL 컨테이너를 띄우고, 테스트는 로컬 JVM에서 JDBC로 그 컨테이너에 접속하는 방식을 사용한다.

- 컨테이너 정의는 `docker-compose.yml`에 두고 개발자가 직접 기동한다. 포트는 `5432`로 고정하며, 접속 정보는 `application-test.yml`에 그대로 기록한다.
- 테스트 컨테이너의 계정 정보는 로컬 전용 값이므로 저장소에 커밋한다.
- 컨테이너는 팀원 각자의 로컬에서 개별적으로 실행된다. 공유 데이터베이스 서버가 아니며, 통일되는 것은 데이터가 아니라 **엔진 버전과 설정**이다.

**Testcontainers는 지금 도입하지 않는다.** 다음 중 하나가 발생하면, 도입을 다시 검토한다.

- 데이터베이스 외에 Redis, Kafka 등 컨테이너로 띄울 의존성이 늘어날 때
- 컨테이너를 직접 기동해야 하는 마찰이 실제 개발 흐름을 방해할 때

## 결과 (Consequences)

**긍정적 영향**

- 운영과 동일한 PostgreSQL로 테스트하므로, 데이터베이스 고유 기능에 의존하는 코드도 검증된다.
- 팀원 전원이 동일한 엔진 버전과 설정을 사용해, 테스트 실패가 환경 차이에서 비롯되는 경우가 사라진다.
- 컨테이너가 계속 살아 있으므로 테스트 실행마다 기동 시간이 들지 않는다.
- DBeaver나 IntelliJ Database 탭으로 직접 접속해 데이터를 확인할 수 있다. 테스트가 실패한 원인을 파악할 때 유용하다.
- 로컬 서버를 띄워 수동으로 확인할 때도 같은 데이터베이스를 사용한다.
- 설정이 `docker-compose.yml` 하나로 끝나며 테스트 코드에 영향을 주지 않는다.

**부정적 영향**

- 개발자가 컨테이너를 직접 기동해야 한다. 띄우지 않은 채 테스트를 실행하면 연결 실패로 중단된다.
- 실행 간 데이터가 누적된다. 테스트 격리를 테스트 코드에서 직접 처리해야 한다.
- 로컬에 PostgreSQL이 이미 설치되어 있으면 5432 포트가 충돌한다.
- CI를 도입할 때 기동·헬스체크·정리 단계를 워크플로우에 직접 작성해야 한다. 데이터베이스가 준비되기 전에 접속하면 실패하므로 대기 처리가 필요하다.
- Docker Desktop 설치가 선행 조건이 된다.

**중립적 영향**

- 테스트 간 데이터 격리 방식(트랜잭션 롤백, 테이블 정리 등)을 별도로 정해야 한다. 이 결정은 Testcontainers를 도입하더라도 동일하게 필요하다.
- CI 구성 시점에 이 결정을 재검토한다. 그 시점에는 Testcontainers의 이점이 비용을 넘어설 가능성이 높다.

## 검토한 대안 (Options Considered)

**대안 1: H2 등 인메모리 데이터베이스 사용**

설치가 필요 없고 실행이 가장 빠르다. 그러나 PostgreSQL 고유의 문법과 타입에서 동작이 달라, 테스트를 통과한 코드가 운영에서 실패할 수 있다. 호환 모드를 켜도 차이가 완전히 사라지지 않는다. 테스트 환경을 운영과 맞춘다는 목적에 어긋나 선택하지 않았다.

**대안 2: Testcontainers 사용**

컨테이너의 생성과 종료를 테스트 코드가 관리하는 방식이다. 개발자가 컨테이너를 미리 기동할 필요가 없어 저장소를 클론한 직후에도 테스트가 바로 실행되고, 무작위 포트를 사용하므로 로컬에 PostgreSQL이 설치되어 있어도 충돌하지 않는다. 데이터베이스 외에 Redis 같은 의존성이 추가될 때도 같은 방식으로 다룰 수 있다.

다만 격리에 대한 이점은 제한적이다. 테스트마다 컨테이너를 새로 만들면 지나치게 느려지므로 실제로는 JVM당 하나를 재사용하며, 그 안에서의 데이터 격리는 Docker Compose와 마찬가지로 테스트 코드가 처리해야 한다. 차이는 실행과 실행 사이에만 있다.

선택하지 않은 이유는 세 가지다. 첫째, 테스트를 실행할 때마다 컨테이너 기동 시간이 더해져 반복 실행이 느려진다. 둘째, 컨테이너가 테스트 종료와 함께 사라지므로 로컬 서버를 띄워 수동으로 확인할 데이터베이스를 따로 마련해야 하고, 결국 Docker Compose를 함께 쓰게 된다. 셋째, 현재 컨테이너로 띄울 의존성이 데이터베이스 하나뿐이라 코드로 관리해 얻는 이점이 작다.

도입을 배제한 것이 아니라 시점을 미룬 것이며, 위 조건이 충족되면 재검토한다.

**대안 3: 로컬에 PostgreSQL 직접 설치**

컨테이너 계층이 없어 가장 가볍다. 그러나 팀원마다 설치 버전과 설정이 갈리고 운영체제별 설치 절차도 달라, 환경 통일이라는 목적을 달성하지 못한다.

**대안 4: 공유 개발 데이터베이스 서버 운영**

각자 설치할 필요가 없다. 그러나 여러 명이 동시에 테스트를 실행하면 서로의 데이터를 침범해 테스트가 불안정해지고, 서버 운영 비용과 네트워크 의존이 추가된다.
