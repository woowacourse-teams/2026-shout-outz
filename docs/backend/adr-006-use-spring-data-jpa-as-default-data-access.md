# ADR-006: Spring Data JPA를 기본 데이터 접근 방식으로 사용

### 결정일 및 결정자
- 결정일: 2026.08.19
- 결정자: 조상준(샤를), 최재영(재키), 박다혜(라이)
- 작성자: 조상준(샤를)

## 상태 (Status)

수락됨 (Accepted)

## 컨텍스트 (Context)

Drop-it의 데이터베이스는 서로 연관된 관계형 데이터(사용자, 프로젝트, 카테고리, 좋아요, 북마크, 댓글, 등록 권한 등)를 다룬다. 이에 따라 어플리케이션의 데이터 트랜잭션과 도메인 객체 매핑을 위해, JdbcTemplate, JPA와 같은 JAVA 영역의 데이터 접근 기술을 도입할 필요가 있었다.

결정 과정에서 가장 중요하게 고려한 요소는 서비스 정책과 관계형 데이터의 특성이었으며, 이를 바탕으로 다음과 같은 기준을 도출했다.

1. 관계형 데이터베이스의 데이터 형태를 도메인 모델과 일관되게 매핑할 수 있어야 한다.
   - Drop-it 서비스는 관계형 데이터베이스를 사용한다. 따라서, 연관된 관계형 데이터를 도메인 객체로 일관되게 매핑할 수 있어야 한다.
2. 데이터 접근 과정에서 일반적인 CRUD와 트랜잭션을 안정적으로 처리할 수 있어야 한다.
   - 엔티티 관계, 외래 키, 복합 유일성, 트랜잭션을 애플리케이션과 데이터베이스에서 일관되게 관리해야 한다.
   - 이 과정에서 동일한 코드를 사용하고, 팀원들 간의 익숙한 데이터 접근 도구를 선택하는 것이 학습 비용이 싸다.
3. 카탈로그 서비스 특성상 기본적으로 검색, 정렬과 조회 성능을 제어할 수 있어야 한다.
   - 조회 기능이 많은 서비스에서는 연관관계 조회로 인한 N+1 문제나 불필요한 쿼리 실행이 발생할 수 있으므로, 실행되는 SQL과 조회 전략을 확인하고 제어할 수 있어야 한다.
   - 카테고리, 키워드, 좋아요 수, 최신순/인기순 등 서비스 정책에 따른 검색·정렬 조건을 유연하게 조합할 수 있어야 한다.

## 결정 (Decision)

아래는 우선순위를 기준으로 작성되었다.

1. **기본 원칙:** Drop-it 백엔드는 Spring Data JPA와 Hibernate를 기본 데이터 접근 방식으로 채택한다. JPA는 엔티티 관계 매핑, CRUD, 트랜잭션 관리에 사용하며, 외래 키와 복합 유일성은 PostgreSQL 제약 조건으로 보장한다.
2. **조회 쿼리 제어가 필요한 경우:** JPA의 기본 메서드나 자동 생성 쿼리만으로 동적 검색, 정렬 조건을 구성하기 어려운 경우에는 QueryDSL로 필요한 컬럼, 조인, 조건, 정렬을 명시한다.
3. **PostgreSQL 특화 기능이 필요한 경우:** 서비스 큐레이션 특성상, **복잡한 집계, 배열, JSONB 조회와 같은 PostgreSQL의 기능이 필요한 경우**, 이를 활용하기 위해 native SQL로 처리하기로 한다.
4. **상황에 따라 유연한 대책:** N+1 문제나 쿼리 성능 문제가 발생하면 생성된 SQL과 실행 횟수를 확인한 뒤 조회 전략을 개선할 수 있다. 이는 팀 내에 협의를 바탕으로 진행하도록 한다.

**최종 결론:** 카탈로그 서비스의 기본 데이터 접근 방식은 JPA로 통일한다. 다만 JPA만으로 표현하거나 성능을 제어하기 어려운 조회에는 QueryDSL을, PostgreSQL 특화 기능에는 native SQL을 보완적으로 사용한다.

## 결과 (Consequences)

**긍정적 영향**: 반복적인 CRUD 코드를 줄이고 도메인 객체와 관계형 데이터를 일관된 방식으로 매핑할 수 있다. Spring Data 기반의 저장소 추상화를 사용할 수 있으며, 복잡한 조회에는 QueryDSL과 native SQL을 선택적으로 적용할 수 있다.

**부정적 영향**: JPA의 영속성 컨텍스트, 지연 로딩, 연관관계 매핑을 이해해야 한다. 잘못된 조회 전략은 N+1이나 불필요한 데이터 조회로 이어질 수 있다. JPA와 QueryDSL 또는 다른 접근 방식을 혼용하면 데이터 접근 규칙과 테스트 범위가 복잡해질 수 있다. 하지만 JPA의 팀 내 학습곡선이 완만하다고 판단되었기에 이와 같은 부정적 영향이 크지 않다고 판단했다.

## 검토한 대안 (Options Considered)

**대안 1**: 쿼리를 쉽게 제어하기 위해, JdbcTemplate을 기본으로 사용한다. 조회에서 실행되는 SQL을 직접 제어하기 쉽지만, 반복적인 매핑과 CRUD 코드를 직접 관리해야 하므로 기본 데이터 접근 방식으로 선택하지 않았다.

**대안 2**: JPA만 사용하고 복잡한 조회도 모두 JPA API로 처리한다. 기술 구성을 단순하게 유지할 수 있지만, 카탈로그 서비스 성격상 동적 검색, 정렬 조건이 증가할 것이라고 판단하였다. 이에 따라, 쿼리 표현력이 제한될 수 있어 QueryDSL을 조건부 대안으로 남겼다.
