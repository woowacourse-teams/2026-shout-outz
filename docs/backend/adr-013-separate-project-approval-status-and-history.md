# ADR-013: 프로젝트의 현재 승인 상태와 승인 이력을 분리해 관리

### 결정일 및 결정자
- 결정일: 2026.08.19
- 결정자: 조상준(샤를), 최재영(재키), 박다혜(라이)
- 작성자: 조상준(샤를)

## 상태 (Status)

수락됨 (Accepted)

대체된 경우: 해당 없음

## 컨텍스트 (Context)

사용자가 등록하는 프로젝트는 등록 심사를 거치며, 현재 심사 상태를 빠르게 조회할 수 있어야 한다. 동시에 승인, 반려, 재심사와 같은 상태 변경 과정과 반려 사유를 보존해야 한다.

`projects`의 현재 승인 상태만 갱신하면 이전 상태와 변경 주체를 확인할 수 없다. 반대로 이력 테이블만 사용하면 목록 조회와 공개 여부 판단 때마다 최신 상태를 계산해야 한다.

## 결정 (Decision)

프로젝트의 현재 심사 상태는 `projects.approval_status`에 저장하고, 상태가 변경될 때마다 `project_approval_histories`에 새로운 이력을 추가한다.

현재 지정된 `projects.approval_status` 값은 다음과 같다: `PENDING`, `APPROVED`, `REJECTED`

승인 이력에는 변경 전 상태, 변경 후 상태, 변경 주체, 변경 사유, 변경 시각을 기록한다. 이력 행은 수정하거나 삭제하지 않고 추가와 조회만 허용한다. 승인 상태 변경 주체는 관리자 권한으로 제한한다.

승인 사유는 외부에 공개할 수 있는 데이터로 취급한다. 따라서 내부 운영자만 확인해야 하는 메모가 필요해지면 승인 사유와 분리된 별도 필드를 추후 설계할 필요가 있다.

해당 행이 사용자 유스케이스에서 조회되는 경우는, 사용자에게 반려 사유를 보여 줘야 할 때 뿐이다. 반려 사유는 `projects.approval_status`가 `REJECTED`인 프로젝트의 `id`로 찾고, `ORDER BY` 날짜 내림차순으로 정렬한 뒤 첫번째 데이터를 반환하는 방식으로 구현한다.

## 결과 (Consequences)

**긍정적 영향**: 프로젝트의 현재 승인 상태를 `projects`에서 빠르게 조회할 수 있다. 모든 승인 상태 변경과 변경 주체 및 사유를 추적할 수 있다. 반려된 프로젝트에 반려 사유를 제공할 수 있고, 이력 데이터를 감사와 운영 분석에 활용할 수 있다.

**부정적 영향**: 상태 변경 때 현재 상태와 이력 테이블을 함께 갱신해야 하므로 트랜잭션 처리가 필요하다. 상태 변경 이력이 계속 쌓이고, 잘못된 상태 전이를 막기 위한 검증 규칙을 구현해야 한다. 공개 사유와 내부 운영 메모를 분리하지 않으면 정보 공개 범위를 통제하기 어렵다.

**중립적 영향**: `PENDING`, `APPROVED`, `REJECTED` 상태 간 허용되는 전이 규칙을 애플리케이션에서 정의한다. 현재 상태와 가장 최근 이력의 일관성을 보장하는 저장 및 조회 API를 설계한다.

## 검토한 대안 (Options Considered)

**대안 1**: `projects.approval_status`만 갱신한다. 현재 상태 조회는 단순하지만 이전 승인 상태, 변경 주체, 반려 사유를 보존할 수 없으므로 선택하지 않았다.

**대안 2**: 승인 상태를 `project_approval_histories`에서만 관리한다. 변경 이력은 자연스럽게 남지만 현재 상태를 조회할 때마다 최신 이력을 계산해야 하고 목록 조회와 공개 여부 판단이 복잡해지므로 선택하지 않았다.
