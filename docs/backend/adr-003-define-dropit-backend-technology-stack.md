# ADR-003: Drop-it 백엔드 기술 스택을 정의

### 결정일 및 결정자
- 결정일: 2026.08.19
- 결정자: 조상준(샤를), 최재영(재키), 박다혜(라이)
- 작성자: 박다혜(라이)

## 상태 (Status)

수락됨 (Accepted)

## 컨텍스트 (Context)

Drop-it 백엔드는 서비스 등록, 사용자, 댓글, 좋아요, 북마크 등의 기능을 제공하기 위해 애플리케이션 개발, 데이터 접근, 인증 및 인가, 테스트, 문서화와 배포에 사용할 기술을 일관되게 정의해야 한다.

애플리케이션 서버를 도입하기로 한 배경과 범위는 ADR-001에서, 운영 데이터베이스의 이전은 ADR-002에서 결정했다. 이 문서는 두 결정을 실행할 기술을 정한다.

개별 기술의 상세 설정과 운영 절차는 별도 ADR에서 결정한다.

## 결정 (Decision)

Drop-it 백엔드는 다음 기술 스택을 기준으로 개발하고 운영한다.

### 현재 사용 기술

| 구분 | 기술 | 적용 내용                                               |
| --- | --- |-----------------------------------------------------|
| 언어 | Java 21 LTS | 백엔드 애플리케이션 개발                                       |
| 프레임워크 | Spring Boot 4.1.1 | 백엔드 애플리케이션 구성 및 실행                                  |
| 웹 서버 | Spring MVC + Tomcat | 동기식 REST API 제공                                     |
| 빌드 도구 | Gradle Wrapper 9.6.0 | 의존성 관리 및 빌드 환경 고정                                   |
| 데이터 접근 | Spring Data JPA, Hibernate | 관계형 데이터의 객체 매핑 및 CRUD 처리                            |
| 데이터베이스 | PostgreSQL | 서비스, 사용자, 댓글, 좋아요, 북마크 등의 데이터 저장 (ADR-002)          |
| 데이터베이스 환경 | Amazon RDS for PostgreSQL | 애플리케이션 서버는 개발 초기부터 이 환경에 접속 (ADR-002)               |
| 스키마 관리 | Flyway | 새 스키마를 V1으로 정의하고 이후 모든 변경을 버전 마이그레이션으로 관리 (ADR-002) |
| 커넥션 풀 | HikariCP | 데이터베이스 연결 관리                                        |
| 인가 | Spring Security | 인증 필터 구성 및 API 접근 제어                                |
| 요청 검증 | Spring Boot Validation | API 요청 값의 필수값 및 길이 검증                               |
| 애플리케이션 메트릭 | Spring Boot Actuator | 애플리케이션 상태, 헬스 체크 및 메트릭 수집                           |
| 객체 스토리지 | Amazon S3 | private 버킷에 미디어 원본, 변형본 저장 (ADR-015)                |
| AWS SDK | AWS SDK for Java 2.x | `S3Client`와 `S3Presigner`를 통한 S3 연동 (ADR-015)       |
| 단위·애플리케이션 테스트 | JUnit, Mockito, AssertJ, Spring Boot Test | 서비스 정책 및 애플리케이션 테스트                                 |
| 통합 테스트 | Docker Compose, PostgreSQL 컨테이너 | 운영과 동일한 엔진으로 통합 테스트 실행 (개발자가 직접 기동)                 |

풀 크기는 RDS 인스턴스의 최대 커넥션 수에 맞춰 산정

### 결정되지 않은 항목

다음은 이 문서에서 확정하지 않으며, 별도 ADR에서 결정한다. 그 전까지는 해당 기능을 구현하지 않는다.

| 항목 | 결정 문서 | 비고                                                                                                                                                             |
| --- | --- |----------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 인증 방식 |  | ADR-002에서 Supabase Auth 의존을 제거하기로 했으므로, 서버가 GitHub OAuth를 직접 처리하고 인증 상태도 직접 관리하게 된다. 따라서 그 상태를 세션과 토큰 중 어떤 방식으로 유지할지 결정해야 한다.                                  |
| API 문서화 방식 |  | 프론트엔드가 서버 API로 전환하려면, API 명세를 정해야 한다. 명세를 컨트롤러 코드에서 자동 생성할지(springdoc-openapi), 컨트롤러 테스트에서 생성할지(Spring REST Docs) 결정한다.                                        |

### 조건부 도입 예정 기술

다음 기술은 현재 기준으로 확정된 사용 기술이 아니다. 해당 조건에 대한 요구사항이 발생하면 별도의 검토와 의사결정을 거쳐 도입한다. 이미 별도 ADR에서 기준을 확정한 기술은 이 목록에서 제외한다.

| 기술 | 도입 검토 조건 | 적용 목적 |
| --- | --- | --- |
| QueryDSL 또는 JOOQ | JPA만으로 처리하기 어려운 동적 검색, 정렬 조건이 증가할 때 | 타입 안전한 동적 쿼리 구성 |
| PostgreSQL 전문 검색 (`pg_trgm`, `tsvector`) | 서비스명, 설명 검색의 정확도나 성능이 단순 패턴 일치로 부족해질 때 | 인덱스 기반 검색 |
| 추가 OAuth 제공자 | GitHub 외의 로그인을 지원할 때 | 로그인 제공자 확장 |
| AWS EC2 | 운영환경을 AWS에 배포할 때 | 실행 가능한 JAR와 환경 변수를 이용한 서버 배포 |
| Testcontainers | CI 파이프라인을 구성할 때, 실행 간 데이터 누적으로 격리 문제가 발생할 때, 또는 DB 외 미들웨어가 늘어날 때 | 테스트 코드가 컨테이너 수명을 관리하는 통합 테스트 환경 |

조건부 도입 예정 기술은 도입 시점에 현재 기술 스택과의 호환성, 운영 비용, 마이그레이션 범위, 보안 요구사항을 다시 검토한다.

## 결과 (Consequences)

### 긍정적 영향

백엔드 개발과 운영에 필요한 기술의 기준을 팀이 공유할 수 있다. 애플리케이션 서버가 개발 초기부터 최종 데이터베이스 환경에 접속하므로, 개발 도중 접속 대상이 바뀌지 않는다.

### 부정적 영향

Spring, JPA, Spring Security를 함께 운영해야 하므로 기술 학습과 설정 관리 비용이 발생한다.

### 중립적 영향

이 ADR은 기술 스택의 기준을 정의할 뿐 각 기술의 상세 설정과 운영 절차까지 결정하지 않는다. 이외의 요구사항이 확정될 때 별도로 결정한다.

## 검토한 대안 (Options Considered)

**대안**: 기능이 필요해질 때마다 기술을 개별적으로 선택한다. 단기적으로는 문서 작성 비용을 줄일 수 있지만, 기술 선택 기준과 현재 사용 여부가 분산되어 팀의 개발·운영 환경을 일관되게 관리하기 어렵다. 공통 기준을 먼저 정의하기 위해 선택하지 않았다.
