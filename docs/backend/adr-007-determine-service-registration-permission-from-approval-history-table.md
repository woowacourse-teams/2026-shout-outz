# ADR-007: 서비스 등록 권한을 승인 기록 테이블로 판단

### 결정일 및 결정자
- 결정일: 2026.08.19
- 결정자: 조상준(샤를), 최재영(재키), 박다혜(라이)
- 작성자: 최재영(재키)

## 상태 (Status)

수락됨 (Accepted)

## 컨텍스트 (Context)

프로젝트는 관리자 심사를 거쳐 게시되며, 심사 결과는 `PENDING`, `APPROVED`, `REJECTED` 상태를 가진다.

프로젝트는 한 번의 심사로 끝나지 않고, 반려 후 수정하여 다시 승인받는 등 상태가 여러 번 변경될 수 있다.

`projects` 테이블에 현재 승인 상태와 마지막 반려 사유만 저장하면 이전에 어떤 승인/반려 과정이 있었는지 알 수 없다.

⇒ 따라서 현재 상태와 상태 변경 이력을 분리해 관리할 필요가 있다.

## 결정 (Decision)

프로젝트의 **현재 승인 상태는 `projects.approval_status`에 저장**하고, 승인 상태가 변경될 때마다 `project_approval_histories`에 새로운 이력을 추가한다.

이력에는 다음 정보를 기록한다.

- 변경 전 상태
- 변경 후 상태
- 변경한 관리자
- 승인 메모 또는 반려 사유
- 변경 시각

승인 이력은 기존 행을 수정하지 않고 **INSERT만 수행하여 과거 심사 기록을 보존한다.**

현재 승인 여부를 판단할 때는 `projects.approval_status`를 사용하고, 과거 승인/반려 과정이나 반려 사유가 필요한 경우 승인 이력 테이블을 조회한다.

## 결과 (Consequences)

**긍정적 영향**: 현재 상태 조회는 `projects`만으로 단순하게 유지하면서도, 여러 번의 승인/반려 과정을 모두 보존할 수 있다. 상태가 변경되더라도 이전 심사 결과와 사유가 유실되지 않는다.

**부정적 영향**: 승인 상태를 변경할 때 `projects` 수정과 승인 이력 추가를 함께 처리해야 하므로 두 데이터의 정합성을 보장해야 한다.

## 검토한 대안 (Options Considered)

**대안 1**: `projects`에 현재 승인 상태와 마지막 반려 사유만 저장한다. 구현은 단순하지만 상태가 다시 변경되면 이전 승인/반려 기록이 사라지므로 선택하지 않았다.

**대안 2**: 승인 상태 자체를 이력 테이블에서만 관리하고 가장 최근 이력을 현재 상태로 사용한다. 데이터 중복은 줄일 수 있지만 프로젝트 조회마다 최신 이력을 찾아야 하므로, 현재 상태는 `projects`에 유지하고 이력만 별도로 관리하기로 했다.
