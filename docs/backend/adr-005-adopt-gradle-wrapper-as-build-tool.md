# ADR-005: Gradle Wrapper를 빌드 도구로 채택

### 결정일 및 결정자
- 결정일: 2026.08.19
- 결정자: 조상준(샤를), 최재영(재키), 박다혜(라이)
- 작성자: 최재영(재키)

## 상태 (Status)

수락됨 (Accepted)

## 컨텍스트 (Context)

백엔드 프로젝트의 의존성 관리, 컴파일, 테스트, 패키징을 일관되게 수행하기 위해 빌드 도구를 선택해야 한다.

후보로 Maven과 Gradle을 검토했다. Maven은 XML 기반의 `pom.xml`을 중심으로 빌드를 선언하는 반면, Gradle은 DSL을 통해 빌드 설정을 코드에 가까운 형태로 작성할 수 있다.

팀은 빌드 설정을 읽고 수정할 때 Gradle의 표현 방식이 더 간결하고 이해하기 쉽다고 느꼈고, 이후 빌드 로직을 확장하기에도 적합하다고 판단했다.

## 결정 (Decision)

백엔드의 빌드 도구로 **Gradle**을 사용한다.

실행은 저장소에 포함된 **Gradle Wrapper**를 기준으로 의존성 관리, 애플리케이션 빌드, 테스트 실행은 저장소에 포함된 Wrapper를 기준으로 수행한다.

프로젝트 채택 당시 Wrapper 기준 버전은 `9.6.0`이고, 이후 버전 변경은 빌드 설정에서 관리한다.

## 결과 (Consequences)

**긍정적 영향**: 빌드 설정을 코드에 가까운 DSL로 관리할 수 있어서 설정을 읽고 수정하기 쉽다. Wrapper를 통해 개발환경과 CI에서 동일한 Gradle 버전으로 빌드할 수 있다. 의존성 관리와 테스트 실행을 하나의 빌드 흐름으로 통합할 수 있다.

**부정적 영향**: Gradle DSL과 빌드 생명주기를 학습해야 한다. 빌드 로직을 과도하게 확장하면 설정 자체가 복잡해질 수 있다.

**중립적 영향**: Gradle 버전 업그레이드는 Spring Boot와 플러그인 호환성을 확인한 뒤 진행한다.

## 검토한 대안 (Options Considered)

**대안 1**: Maven을 사용한다. Java 생태계에서 널리 사용되고 규칙이 명확하다는 장점이 있지만, 이 프로젝트에서는 코드 기반 빌드 설정의 가독성과 확장성을 우선하기 위해 선택하지 않았다.
