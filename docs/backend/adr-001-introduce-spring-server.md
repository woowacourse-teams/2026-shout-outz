# ADR 001: 운영환경에 Spring 서버를 애플리케이션 계층으로 도입한다

## 상태 (Status)

수락됨 (Accepted)

## 컨텍스트 (Context)

프로토타입은 React 프론트엔드가 Supabase Auth와 Data API 및 RPC를 직접 호출하고, RLS·제약 조건·트리거·PostgreSQL 함수가 데이터 접근과 일부 비즈니스 규칙을 담당하는 구조다. 빠른 기능 검증에는 적합하지만, 규칙이 프론트엔드와 데이터베이스에 분산되어 변경·장애 추적·테스트가 어렵다.

실서비스 전환의 목표는 다음 세 가지 안정성을 확보하는 것이다.

1. 서비스가 제공하는 데이터를 신뢰할 수 있어야 한다.
2. 서비스 규칙을 배포 전에 검증할 수 있어야 한다.
3. 운영 작업을 사람의 개입 없이 반복 실행할 수 있어야 한다.

현재 구조에는 다음과 같은 한계가 있다.

- **데이터 신뢰성**: `increment_app_plays`는 `anon` 롤에 실행 권한을 부여하고, `record_site_visit`은 클라이언트가 전달한 방문자 식별자를 그대로 받는다. `verify_crew_access_code`에도 시도 횟수 제한이 없다. 따라서 실행 수·방문자 수 조작과 인증 코드 무제한 대입을 막기 어렵다. 특히 실행 수와 방문자 수가 인기순·추천 기준에 사용되면 핵심 화면이 왜곡될 수 있다.
- **배포 전 검증**: 답글 깊이 제한과 입력 길이 검증 같은 규칙이 테이블 제약 조건, 트리거, PL/pgSQL 함수에 흩어져 있다. 데이터베이스 통합 테스트는 가능하지만, 프론트엔드 단위 테스트만으로 규칙을 일관되게 검증하기 어렵고 오류 응답도 API 계약으로 통합하기 어렵다.
- **운영 자동화**: `VITE_` 환경 변수는 브라우저에 노출되므로 비밀 정보가 필요한 작업을 프론트엔드에서 실행할 수 없다. 그 결과 이전 기수 프로젝트 데이터 수집을 로컬에서 수동 실행하고 JSON을 커밋해야 하며, 정기 실행·실패 감지·재처리를 자동화하기 어렵다.

따라서 Spring 서버는 Supabase를 다른 데이터베이스로 교체하기 위해 도입하지 않는다. 브라우저와 데이터 저장소 사이에 애플리케이션 계층을 두고 운영 정책과 비즈니스 규칙을 집행하며, 서버 권한이 필요한 작업과 반복 작업을 자동화하기 위해 도입한다.

팀이 백엔드 서버의 설계·운영 경험을 확보하려는 목표도 이 결정에 반영한다. 운영 데이터베이스의 이전 여부는 Spring 도입과 독립된 사안이며 별도 ADR에서 다룬다. Spring 서버는 Supabase PostgreSQL을 유지하는 상태에서도 도입할 수 있다.

## 결정 (Decision)

운영환경에서는 Spring 서버를 애플리케이션/API 계층으로 도입한다.

Spring 서버는 인증된 사용자를 식별하고, 도메인 권한, 입력 검증, 비즈니스 규칙, 트랜잭션, 요청 제한, 운영 로그를 관리한다. 프론트엔드는 주요 도메인 기능을 Spring API를 통해 호출하며, 데이터베이스의 테이블과 저장 프로시저를 직접 호출하는 의존성을 단계적으로 줄인다.

Spring 서버는 단순한 CRUD 중계 계층으로 구현하지 않는다. 서비스의 정책과 유스케이스를 소유하는 계층으로 구현해 프론트엔드와 데이터 저장소의 결합을 낮춘다.

이 ADR은 Spring 서버 도입만 결정한다. Supabase에서 RDS PostgreSQL로 데이터베이스를 마이그레이션할지 여부와 그 이유는 별도의 ADR에서 결정한다.

## 결과 (Consequences)

**긍정적 영향**: 비즈니스 규칙과 권한 검사를 한곳에서 관리할 수 있다. 요청 제한, 중복 요청 방지, 감사 로그와 같은 운영 제어를 적용할 수 있다. 여러 데이터 변경을 하나의 유스케이스와 트랜잭션으로 묶을 수 있다. 프론트엔드가 데이터베이스 스키마에 직접 의존하지 않으므로 API 계약과 저장소를 독립적으로 변경하기 쉬워진다.

**부정적 영향**: 별도의 Spring 애플리케이션을 개발·배포·모니터링해야 한다. 프론트엔드와 Supabase 사이에 네트워크 계층이 추가되어 구조와 장애 지점이 늘어난다. 인증 토큰 전달, 예외 처리, API 계약, 서버와 데이터베이스 간 권한 설계를 새로 정의해야 한다. 기존 Supabase 직접 호출을 Spring API 호출로 단계적으로 전환해야 한다.

**중립적 영향**: 초기 전환 범위와 순서를 정해야 한다. 인증 제공자와 데이터 저장소를 Spring 도입과 동시에 변경하지 않고 별도 의사결정으로 분리할 수 있다. Supabase의 RLS와 RPC를 어떤 시점까지 유지할지 후속 설계에서 정한다. 데이터베이스 마이그레이션은 별도 ADR에서 다룬다.

## 검토한 대안 (Options Considered)

**대안 1**: 프론트엔드가 Supabase에 직접 접근하는 현재 구조를 유지한다. 프로토타입을 빠르게 운영할 수 있지만, 비즈니스 규칙이 React 코드와 RLS 및 RPC에 분산된다. 운영에 필요한 요청 제한, 감사 로그, 관리자 정책과 복합 트랜잭션을 일관되게 적용하기 어렵기 때문에 선택하지 않았다.

**대안 2**: 필요한 기능만 Supabase Edge Functions로 구현한다. 서버 운영 부담을 줄이면서 일부 민감한 작업을 서버 측으로 옮길 수 있지만, 도메인 유스케이스와 API 계약을 확장 가능한 애플리케이션 계층으로 통합하기 어렵다. Spring 기반의 명시적인 계층 구조와 테스트·운영 체계를 사용하기 위해 선택하지 않았다.
