# ADR 009: users와 user_profiles 테이블을 분리한다

## 상태 (Status)

수락됨 (Accepted)

대체된 경우: 해당 없음

## 컨텍스트 (Context)

사용자 계정에는 계정 상태, 권한, 마지막 로그인 시각, 생성·수정 시각, 탈퇴 시각처럼 서버의 계정 관리에 필요한 정보가 있다. 반면 서비스 화면에는 핸들, 표시 이름, 소속, 직무, 자기소개, 프로필 이미지처럼 다른 사용자에게 공개할 프로필 정보가 필요하다.

계정 관리 정보와 공개 프로필 정보를 한 테이블에 저장하면 공개 API가 계정 생명주기와 권한 정보에 접근할 가능성이 커진다. 또한 PostgreSQL은 행을 수정할 때 새 행 버전을 생성하므로, 자주 변경되는 계정 관리 정보와 상대적으로 변경 빈도가 낮은 프로필 정보를 분리하면 불필요한 데이터 변경 범위를 줄일 수 있다.

프로필 정보를 조회할 때 조인이 추가되지만, 사용자와 프로필은 1:1 관계이고 조인 비용을 감수할 수 있다고 판단했다.

## 결정 (Decision)

계정 관리 정보는 `users` 테이블에 저장하고, 서비스에서 공개하는 사용자 정보는 `user_profiles` 테이블에 저장한다.

`user_profiles.user_id`를 `users.id`를 참조하는 기본키이자 외래키로 사용해 두 테이블의 1:1 관계를 표현한다. `users`는 계정 상태, 권한, 로그인 및 생명주기를 관리하고, `user_profiles`는 핸들, 표시 이름, 소속, 직무, 자기소개, 프로필 이미지와 같은 공개 프로필을 관리한다.

회원가입 시 OAuth 연결 정보에서 기본 프로필 이미지를 가져와 `user_profiles`를 초기화한다. 공개 API는 필요한 프로필 컬럼만 조회하고, 계정 관리 컬럼은 공개하지 않는다.

## 결과 (Consequences)

**긍정적 영향**: 계정 보안과 공개 프로필의 접근 범위를 분리할 수 있다. 프로필 필드를 확장해도 인증 및 계정 관리 테이블의 책임이 커지지 않는다. 계정 관리 정보가 변경될 때 프로필 정보까지 함께 갱신하는 일을 줄일 수 있다.

**부정적 영향**: 사용자와 프로필을 함께 조회할 때 조인이 필요하다. 회원가입·탈퇴·복구 과정에서 두 테이블의 상태를 함께 관리해야 한다. 댓글이나 프로젝트 목록처럼 사용자 표시 정보가 자주 필요한 조회에는 조인과 조회 전략이 필요하다.

**중립적 영향**: 프로필 조회 API와 인덱스 전략을 별도로 설계한다. 프로필 이미지나 표시 이름을 읽기 성능을 위해 다른 도메인에 비정규화할지는 실제 조회 패턴을 확인한 뒤 결정한다.

## 검토한 대안 (Options Considered)

**대안 1**: 계정 정보와 프로필 정보를 `users` 한 테이블에 저장한다. 조인이 없어 조회와 구현이 단순하지만, 공개 정보와 서버 전용 정보의 보안 경계가 약해지고 프로필 확장 시 계정 테이블의 책임이 커지므로 선택하지 않았다.

**대안 2**: 자주 표시하는 닉네임과 프로필 이미지만 `users`에 두고 나머지 프로필 정보를 `user_profiles`로 분리한다. 일부 조회의 조인을 줄일 수 있지만, 공개 프로필과 계정 관리 정보의 경계를 다시 흐리게 하고 데이터 동기화 지점을 늘리므로 선택하지 않았다.
