# ADR 013: 운영 데이터베이스를 Amazon RDS for PostgreSQL로 이전한다

## 상태 (Status)

수락됨 (Accepted)

대체된 경우: 해당 없음

## 컨텍스트 (Context)

Dropit은 현재 Supabase가 제공하는 관리형 PostgreSQL을 사용한다. 프로토타입에서는 빠르게 기능을 검증할 수 있었지만, 운영환경에서는 다음을 팀의 기준으로 관리해야 한다.

- 스키마 변경 이력과 환경 간 동일성
- 백업 보관 기간, RPO, RTO와 복구 절차
- 데이터베이스의 지속성 및 운영환경과의 통합

현재 스키마·RLS 정책·PostgreSQL 함수는 `supabase/schema.sql`에 누적되어 대시보드에서 수동으로 실행한다. 이 방식은 운영 데이터베이스의 실제 상태와 변경 이력을 추적하기 어렵고, 변경을 버전 단위로 되돌리기 어렵다. 또한 현재 사용 중인 플랜의 일시 정지 정책은 트래픽이 간헐적인 아카이빙 서비스의 지속성 리스크가 된다.

### PostgreSQL을 선택한 이유

Dropit은 초기 CRUD를 넘어 카테고리·태그 필터링, 좋아요·실행 수 기반 랭킹, 방문자 집계, 승인·삭제 이력, 댓글 계층 조회를 처리해야 한다. 이후 JSON 메타데이터, 전문 검색, 부분·표현식 인덱스와 같은 요구사항도 추가될 수 있다.

PostgreSQL은 관계형 무결성을 유지하면서 이러한 복잡한 조회와 집계를 확장할 수 있고, 현재 Supabase도 PostgreSQL을 사용한다. 따라서 PostgreSQL을 유지하면 SQL과 데이터 타입의 변환 범위를 줄일 수 있다. MySQL도 기본 CRUD를 처리할 수 있지만, 현재 도메인에서 엔진을 변경해야 할 만큼의 이점은 확인되지 않았다.

### Amazon RDS를 선택한 이유

우리는 우아한테크코스 팀 프로젝트로 AWS 자원을 지원받고 있다. 따라서 AWS 환경과 데이터베이스를 통합하고, 지원받은 자원을 활용해 운영 비용 부담을 낮출 수 있다.

Amazon RDS for PostgreSQL은 호스트 운영과 일부 인프라 관리 부담을 줄이면서도, Supabase보다 네트워크·백업·파라미터·운영 환경을 팀의 서비스 구조에 맞게 관리할 수 있는 범위를 넓혀 준다. RDS는 완전한 무관리 서비스가 아니므로 백업 검증, 모니터링, 장애 대응과 같은 데이터베이스 운영 책임은 팀이 맡는다.

## 결정 (Decision)

운영 데이터베이스를 Amazon RDS for PostgreSQL로 이전한다. 데이터베이스 엔진은 PostgreSQL로 유지하고, Supabase에서 RDS로 데이터베이스 운영 환경만 이전한다.

이전은 다음 순서로 수행한다.

1. Flyway를 도입하고 현재 운영 데이터베이스를 `V1__baseline.sql`로 기준화한다. 이후 스키마 변경은 버전이 부여된 마이그레이션으로만 수행한다.
2. ADR-001의 Spring 서버가 데이터 접근을 담당하도록 전환한다. 서버 전환 중에는 Supabase PostgreSQL을 계속 사용할 수 있다.
3. `auth.users` 외래 키 의존성을 해소할 인증 이전 계획을 별도 ADR로 결정하고 실행한다.
4. 사용자 식별자 매핑과 데이터 검증 계획을 수립한 뒤, 점검 시간에 데이터를 RDS로 이전하고 트래픽을 전환한다.

Spring의 인가 로직과 데이터베이스 보안 정책을 검증할 때까지 데이터베이스 수준의 방어 정책을 필요한 범위에서 유지한다. Supabase의 `auth.uid()`에 의존하는 RLS 표현식과 `security definer` 함수는 새 인증 방식에 맞게 대체하거나 재구현한다. Supabase Storage의 파일 이전과 최종 객체 저장소 선택은 별도 ADR에서 결정한다.

## 결과 (Consequences)

**긍정적 영향**: PostgreSQL의 관계형 무결성과 복잡한 조회·집계 기능을 유지하면서 엔진 변경 비용을 줄인다. Flyway로 스키마 변경을 버전 관리하고 환경 간 동일성을 높일 수 있다. 백업·복구 정책과 데이터베이스 운영 환경을 서비스 요구사항과 AWS 인프라에 맞춰 관리할 수 있다. Supabase 특화 기능에 대한 의존성을 줄이고 Spring 서버와 데이터베이스의 책임을 명확히 나눌 수 있다.

**부정적 영향**: RDS 비용이 발생하고, 백업 검증·모니터링·커넥션 관리·업그레이드·장애 대응을 팀이 수행해야 한다. 인증 이전이 완료될 때까지 데이터 이전을 시작할 수 없으며, 사용자 식별자 매핑 오류는 작성자·좋아요·북마크 귀속 오류로 이어질 수 있다. 전환 시 점검 시간과 롤백 계획이 필요하다.

**중립적 영향**: `jsonb`·배열 필드의 정규화 여부, `apps.id`의 식별자 형식, `crypt()` 해시 호환성, 애플리케이션과 데이터베이스의 타임존을 이전 과정에서 확정한다. 이전 전후의 주요 쿼리 성능과 데이터 건수를 비교한다.

## 검토한 대안 (Options Considered)

**대안 1**: Amazon RDS for MySQL로 이전한다. MySQL도 기본 CRUD와 일반적인 검색을 처리할 수 있지만, 현재 데이터베이스가 PostgreSQL이고 Dropit의 복잡한 조회·집계·JSON 메타데이터·인덱스 요구를 위해 SQL과 데이터 타입을 추가로 변환해야 한다. 엔진 변경에 따른 비용을 상쇄할 요구사항이 없어 선택하지 않았다.

**대안 2**: Supabase PostgreSQL을 유지하고 Spring 서버만 추가한다. 애플리케이션 계층과 비즈니스 규칙은 개선할 수 있지만, 현재 플랜의 일시 정지 리스크와 백업·복구 정책에 대한 통제 한계가 남는다. 운영 데이터베이스 환경에 대한 통제권을 확보한다는 목표를 달성할 수 없어 선택하지 않았다.

**대안 3**: Supabase의 유료 플랜으로 상향한다. 일시 정지와 백업 관련 제약을 줄일 수 있지만, 복구 목표와 운영 환경에 대한 통제 범위가 Supabase가 제공하는 기능과 정책에 종속된다. AWS 지원 자원을 활용해 RDS를 운영하는 편이 팀의 목표에 더 적합하므로 선택하지 않았다.

**대안 4**: EC2에 PostgreSQL을 직접 설치해 운영한다. 데이터베이스 운영 권한은 가장 넓지만, 패치·백업·장애 복구·고가용성 구성을 모두 팀이 직접 관리해야 한다. AWS 관리형 데이터베이스의 운영 부담 절감 효과를 활용하기 위해 선택하지 않았다.
