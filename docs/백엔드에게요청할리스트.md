# 백엔드에게 요청할 목록

문서에 타입이 없어 프론트가 설명문을 읽고 손으로 적고 있는 값들. enum으로 선언해 주면
`generate:api`가 타입으로 뽑아 주고, 값이 바뀌어도 컴파일 단계에서 알 수 있다.

## 1. 미디어 API를 문서에 추가

`/api/v1/media/*`가 openapi3.yaml에 없다. 동작은 한다.

```
POST /api/v1/media/uploads
POST /api/v1/media/{mediaId}/complete
GET  /api/v1/media/{mediaId}
```

`uploads` 요청 본문의 `purpose`를 enum으로:

```
FEED_CONTENT
HOME_BANNER
PROJECT_DESCRIPTION
PROJECT_THUMBNAIL
USER_AVATAR
```

## 2. 쿼리 파라미터 enum

현재 전부 `type: string`이고 허용값은 description 산문에만 있다.

| 엔드포인트                                | 파라미터      | 값                                |
| ----------------------------------------- | ------------- | --------------------------------- |
| `GET /api/v1/projects`                    | `sort`        | `LATEST`, `POPULAR`               |
| `GET /api/v1/feeds`                       | `sort`        | `LATEST`, `POPULAR`, `RELEVANCE`  |
| `GET /api/v1/feeds/{feedId}/comments`     | `sort`        | `LATEST`, `OLDEST`                |
| `GET /api/v1/news`                        | `type`        | `ALL`, `NOTICE`, `EVENT`          |
| `GET /api/v1/news`                        | `sort`        | `LATEST`                          |
| `GET /api/v1/news`                        | `eventStatus` | `UPCOMING`, `ONGOING`, `ENDED`    |
| `GET /api/v1/admin/verification-requests` | `status`      | `PENDING`, `APPROVED`, `REJECTED` |

## 3. 요청 본문 배열 원소 타입

`FeedSaveRequest` · `FeedUpdateRequest`의 `categoryIds`, `mediaIds`가
`(object | boolean | string | number)[]`로 생성된다. `number[]`가 되도록.

## 4. 작성·수정 응답의 `media[]`에 `mediaId` 추가

조회 응답 셋(`FeedFind`, `FeedFindAll`, `UserFeedFindAll`)에는 있는데
`FeedSaveSuccessResponse` · `FeedUpdateSuccessResponse`에는 없다.

## 5. 홈 배너 대체 텍스트

`GET /api/v1/home/banners` 응답에 alt 텍스트가 없어 스크린리더에서 모든 배너가 같게 읽힌다.

## 6. 데이터 시드

`GET /api/v1/categories`가 빈 배열이라 피드 작성이 막혀 있다(카테고리는 필수).
생성은 관리자 전용이라 프론트에서 넣을 수 없다.

## 7. 관리자 프로젝트 심사 API ✅ 반영됨 (2026-09-29 확인)

아래 요청대로 만들어 주셔서 프론트도 실제 타입으로 교체했습니다. 남은 것은 3번(배열 원소 타입)뿐입니다 —
`AdminProjectFindAllSuccessResponse`의 `members`·`techTags`가 여기서도 `(object | boolean | string | number)[]`로 옵니다.

문서에 아예 없다. 관리자 화면은 이미 만들어져 있고, 인증 신청 심사(`/api/v1/admin/verification-requests`)와
같은 모양으로 **주소와 응답을 프론트가 가정**해서 붙여 뒀다. 아래 모양으로 만들어 주면 프론트는 그대로 동작한다.
다르게 만들 거면 확정된 모양을 알려주면 맞춘다.

가정한 위치: `frontend/src/apis/admin.ts`, 타입은 `frontend/src/types/admin.ts`.

### 7-1. 심사 대상 목록

```
GET /api/v1/admin/projects?status={PENDING|APPROVED|REJECTED}&cursor={cursor}
```

- `status` 필수, enum
- `cursor` 선택. 커서 기반 페이지네이션

응답 항목은 `GET /api/v1/projects`의 목록 항목(`ProjectFindAllSuccessResponse`의 `data[]`)에
아래 두 필드를 더한 모양으로 가정했다.

```
approvalStatus: PENDING | APPROVED | REJECTED
rejectReason: string | null      // REJECTED일 때만 값
```

화면이 실제로 읽는 필드는 이 일곱 개다. 목록 항목 전체를 주기 어렵다면 이것만으로도 된다.

```
id, title, tagline, cohort, members[].displayName, approvalStatus, rejectReason
```

**주의**: 프론트가 가정한 응답 봉투는 `data: { items, nextCursor }`인데,
`#228`에서 목록 응답 규칙이 `data: [...]` + `meta: { hasNext, nextCursor, totalCount }`로 바뀌었다.
새 규칙으로 만들어 주면 프론트가 그쪽에 맞춘다. 가정 쪽이 낡았다.

### 7-2. 승인

```
POST /api/v1/admin/projects/{projectId}/approve
```

요청 본문 없음. 응답 본문도 쓰지 않는다(204 가정).

### 7-3. 반려

```
POST /api/v1/admin/projects/{projectId}/reject
{ "reason": "사유" }
```

응답 본문을 쓰지 않는다(204 가정). `reason`의 필수 여부와 길이 제한을 정해 주면 프론트에서 먼저 검증한다.

### 7-4. 권한

관리자만 접근하는 엔드포인트다. 권한 없는 사용자에게 어떤 코드를 주는지 알려주면 화면에서 구분해 처리한다.
