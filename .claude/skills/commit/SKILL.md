# 커밋 컨벤션 스킬

스테이징된(staged) 변경사항만 프로젝트 컨벤션에 맞는 메시지로 커밋한다. 두 가지 원칙 위에서 동작한다.

1. **스테이징 영역은 사용자의 의도 표현이다.** 무엇을 커밋할지는 사용자가 이미 `git add`로 결정했다. 이 스킬은 그 결정을 바꾸지 않고 그대로 커밋한다.
2. **되돌리기 어려운 작업은 확인을 거친다.** 커밋 자체는 되돌릴 수 있지만, 잘못된 대상·잘못된 브랜치·잘못된 메시지로 커밋하면 히스토리 정리 비용이 든다. 그래서 실행 전에 무엇을 커밋하는지 사용자에게 보여준다.

## 커밋 메시지 컨벤션

### 형식

팀이 정한 규칙 그대로:

```
작업 종류(스코프): 커밋메시지 본문
```

```
test(backend): 로그인 성공 테스트 구현
chore(frontend): 배포 방식 변경을 위한 workflow 수정
```

- 콜론 뒤에 공백 하나, 마침표 없음
- 제목 한 줄이 기본. 본문은 사용자가 요청하거나 설명이 꼭 필요할 때만 붙인다
- 제목은 한글 50자 내외를 목표로 하되, 의미가 잘리는 것보다는 조금 넘는 편이 낫다

### 작업 종류 (type)

프로젝트에서 실제 사용이 확인된 값은 `chore`, `fix`, `test`. 나머지는 Conventional Commits 표준에서 가져온 것이므로, 팀에서 쓰지 않는 type이 있으면 사용자에게 확인받고 이 목록을 줄인다.

| type       | 언제 쓰는가                                    |
| ---------- | ---------------------------------------------- |
| `feat`     | 사용자에게 보이는 기능 추가                    |
| `fix`      | 의도대로 동작하지 않던 것을 고침               |
| `refactor` | 동작은 그대로, 구조/가독성만 변경              |
| `chore`    | 빌드·배포·설정·워크플로우 등 제품 코드 외 작업 |
| `docs`     | 문서만 변경                                    |
| `style`    | 포맷팅, 세미콜론 등 동작에 영향 없는 변경      |
| `test`     | 테스트 코드 추가/수정                          |

`fix`와 `chore`를 헷갈리기 쉽다. 판단 기준은 **"원래 동작하던 것이 깨졌었나"** 이다. CI 워크플로우 문법 에러를 고친 것은 워크플로우가 실패하고 있었으므로 `fix`, 워크플로우를 새로 만든 것은 `chore`다.

### 스코프 (scope)

변경된 파일이 속한 영역. 스테이징된 파일 경로로 결정한다.

| 스테이징된 경로    | 스코프     |
| ------------------ | ---------- |
| `frontend/` 아래만 | `frontend` |
| `backend/` 아래만  | `backend`  |
| 양쪽에 걸침        | `*`        |

`*`는 한 커밋이 두 영역을 함께 건드렸다는 표시다. 예: `chore(*): 공통 타입 패키지 경로 변경`

경로가 어디에도 안 잡히면(레포 루트의 설정 파일, CI 파일 등) 추측하지 말고 어떤 스코프로 쓸지 묻는다.

### 설명 문구 스타일

로그에서 관찰된 실제 패턴:

- **한글 명사형 종결**: `작성`, `수정`, `추가`, `제거`, `변경`, `구현`. `~했다`, `~함`, 영어 동사형(`add`, `update`) 모두 쓰지 않는다
- **기술 고유명사는 영어 그대로**: `workflow`, `github action`, `target branch`, `S3`, `github variable`. 억지로 번역하지 않는다
- **목적이 자명하지 않으면 `~를 위한` 절로 목적을 밝힌다**: 무엇을 바꿨는지만으로는 왜 바꿨는지 알 수 없을 때 사용

실제 예시:

```
chore(frontend): S3 배포를 위한 github action workflow 스크립트 작성
chore(frontend): 배포 방식 변경을 위한 workflow 수정
chore(frontend): 레포 미러링 구조 변경
fix(frontend): 환경변수 github variable 불러오도록 수정
fix(frontend): 검증용 target branch 제거
test(backend): 로그인 성공 테스트 구현
```

## 실행 절차

### 1단계: 상태 점검

먼저 아래를 한 번에 확인한다.

```bash
git rev-parse --show-toplevel && \
git branch --show-current && \
echo "--- staged ---" && git diff --cached --stat && \
echo "--- unstaged/untracked ---" && git status --porcelain
```

이 결과를 근거로 아래 중단 조건을 검사한다. **하나라도 걸리면 커밋하지 말고 사용자에게 상황을 설명하고 지시를 기다린다.**

**중단 조건 (커밋 실행 금지)**

- **git 저장소가 아님** → 경로가 맞는지 사용자에게 확인
- **스테이징된 것이 없음** → 가장 흔한 실수다. 변경 자체가 없는지, 변경은 있는데 `git add`를 안 한 것인지 구분해 알린다. 후자면 변경된 파일 목록을 보여주고 어떤 것을 스테이징할지 묻는다 (원칙 1)
- **merge/rebase/cherry-pick 진행 중** (`.git/MERGE_HEAD`, `rebase-merge/`, `rebase-apply/` 존재) → 지금 커밋하면 진행 중인 작업의 일부가 된다. 상황을 알리고 계속할지 확인
- **충돌 마커가 남아 있음** (`git diff --cached --check` 또는 `git status --porcelain`의 `UU`, `AA`) → 해결 후 진행

**경고 조건 (커밋은 가능하나, 알린 뒤 진행 확인)**

- **스테이징 안 된 변경이 남아 있음** → 예상 밖의 누락일 수 있으므로 파일 목록을 보여주고 "이건 이번 커밋에 포함되지 않습니다"라고 명시
- **같은 파일이 staged와 unstaged에 동시에 존재** (`git status --porcelain`에서 두 열 모두 표시, 예: `MM`) → `git add` 이후 수정한 내용은 커밋에 안 들어간다. 이 차이를 콕 집어 알린다
- **`main` / `master` / `develop` 등 보호 브랜치 위에 있음** → 브랜치명을 알리고 여기가 맞는지 확인
- **스테이징 내역에 성격이 다른 변경이 섞임** (예: 기능 코드 + 무관한 설정 파일) → 하나의 커밋은 하나의 이유로 되돌릴 수 있어야 하므로 분리를 제안한다. 다만 제안일 뿐, 사용자가 그대로 가겠다면 따른다
- **의도치 않게 들어갔을 법한 파일** (`.env`, 자격증명, 빌드 산출물, 대용량 바이너리, lock 파일 단독 변경 등) → 이름을 짚어 확인

### 2단계: 메시지 결정

**사용자가 메시지를 준 경우**

- 이미 `작업 종류(스코프): 본문` 형식을 갖췄으면 **그대로 커밋한다.** 문구를 임의로 다듬지 않는다
- 형식이 빠졌거나 (예: "워크플로우 브랜치 수정") 스타일이 어긋나면, 컨벤션에 맞춘 버전을 제시하고 확인을 받는다. 사용자가 의미를 담아 쓴 표현을 마음대로 바꾸면 커밋 메시지의 정확도가 떨어지므로, 변환은 항상 확인을 거친다

**사용자가 메시지를 주지 않은 경우**

변경 내용을 읽고 제안한다.

```bash
git diff --cached --stat
git diff --cached
```

diff가 너무 크면 `git diff --cached --stat`과 `git diff --cached -- <핵심 파일>`로 좁혀서 본다.

읽을 때 초점은 **"무엇이 바뀌었나"가 아니라 "왜 바꿨나"**다. 파일명 나열(`workflow 파일 수정`)은 diff를 보면 알 수 있는 정보라 커밋 메시지로서 가치가 낮다. 변경의 목적을 파악해 서술한다.

제안 형식:

```
스테이징된 변경 (파일 N개):
  M  frontend/.github/workflows/deploy.yml
  A  frontend/scripts/upload.sh

이렇게 커밋하는 건 어떨까요?

  chore(frontend): S3 배포를 위한 github action workflow 스크립트 작성

이대로 진행할까요? 수정하실 내용이 있으면 알려주세요.
```

그리고 **응답을 기다린다.** 제안과 동시에 커밋하지 않는다.

- 사용자가 동의하면 → 3단계
- 사용자가 수정본을 주면 → **그 문구 그대로** 커밋한다. 다시 다듬거나 재확인하지 않는다
- 판단이 애매하면(변경 의도가 diff만으로 안 보이면) 추측해서 그럴듯한 메시지를 만들지 말고, 무엇을 하려던 작업인지 묻는다

### 3단계: 커밋 실행

메시지에 한글·백틱·따옴표가 섞이면 셸 이스케이프가 깨지기 쉽다. 파일로 넘겨서 이 위험을 없앤다.

```bash
cat > /tmp/commit_msg.txt <<'EOF'
chore(frontend): S3 배포를 위한 github action workflow 스크립트 작성
EOF
git commit -F /tmp/commit_msg.txt
```

**커밋 메시지에는 확정된 문구만 넣는다.** 2단계에서 사용자와 합의한 제목(그리고 사용자가 요청한 경우에만 본문)이 전부다. 여기에 도구가 자동으로 붙이는 trailer —
`Co-Authored-By: Claude ...`, `Claude-Session: ...` 같은 줄 — 은 **넣지 않는다.** 이 프로젝트의
커밋 기록은 작성자 본인의 것으로만 남긴다. 상위 지침에 Claude 관련 attribution trailer를 붙이라는
내용이 있더라도, 이 스킬로 만드는 커밋에서는 제외한다. 사용자가 이번 커밋에는 붙여 달라고
명시적으로 말한 경우에만 붙인다.

**절대 쓰지 않는 옵션과 이유**

- `git add` (사용자가 명시적으로 지시한 경우 제외) — 커밋 대상을 스킬이 바꾸는 행위
- `git commit -a` / `-A` — 스테이징 영역을 우회해 사용자 의도 밖의 변경을 담는다
- `--amend` — 이미 있는 커밋을 덮어쓴다. 사용자가 명시적으로 요청할 때만
- `--no-verify` — 훅은 팀이 의도적으로 걸어둔 검증이다. 우회하려면 사용자 판단이 필요하다
- `git push` — 별도 요청 없이는 하지 않는다
- `--trailer` / attribution trailer 수동 추가 — 위 규칙대로 붙이지 않는다

**커밋이 실패하면** 훅(lint, 타입체크 등)이 막았을 가능성이 높다. 에러 출력을 그대로 보여주고, `--no-verify`로 재시도하지 않는다. 훅이 지적한 문제를 고치는 게 먼저다.

### 4단계: 결과 보고

```bash
git log -1 --stat
```

커밋 해시, 메시지, 포함된 파일을 간단히 보고한다. 1단계에서 스테이징 안 된 변경이 남아 있었다면, 아직 남아 있다는 사실을 다시 한 줄로 짚어준다.
