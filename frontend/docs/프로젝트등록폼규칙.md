### 검증 단계

- **1차 (DTO 어노테이션)**: 실패하면 `400 VALIDATION_FAILED`로 응답하고, `details`에 실패한 필드가 모두 `{field, message}`로 담깁니다.
- **2차 (서비스·도메인)**: 첫 번째 실패에서 바로 멈춥니다. 응답 코드는 에러 코드 이름(예: `PROJECT_INVALID_TECH_TAG`)이고 `details`는 없습니다.
- **문자열은 검증 전에 서버가 앞뒤 공백을 자릅니다.** 대상은 title, teamName, tagline, githubRepositoryUrl, deploymentUrl, memberHandles의 각 항목입니다(descriptionMd 제외). 글자 수도 자른 뒤에 세고, 공백만 있는 값은 입력하지 않은 것으로 봅니다.
- `details[].field`는 보통 요청 필드명이지만, 두 필드를 함께 보는 검증은 검증 메서드 이름이 옵니다. 지금은 `serviceStatusValid` 하나입니다.

### 등록 `POST /api/v1/projects`, 수정 `PUT /api/v1/projects/{projectId}`

#### 필드별 규칙 (실패 시 400 `VALIDATION_FAILED`, `details`에 필드와 메시지 포함)

| 필드                | 등록 | 수정 | 규칙                                                                                                                   |
| ------------------- | ---- | ---- | ---------------------------------------------------------------------------------------------------------------------- |
| title               | 필수 | 필수 | 앞뒤 공백을 자른 뒤 최대 100자, 공백만 있으면 불가                                                                     |
| teamName            | 필수 | 필수 | 앞뒤 공백을 자른 뒤 최대 50자, 공백만 있으면 불가                                                                      |
| tagline             | 필수 | 필수 | 앞뒤 공백을 자른 뒤 최대 200자, 공백만 있으면 불가                                                                     |
| cohort              | 필수 | 필수 | -                                                                                                                      |
| githubRepositoryUrl | 필수 | 필수 | 최대 2,048자, `https://github.com/{owner}/{repo}` 형식                                                                 |
| deploymentUrl       | 선택 | 선택 | 최대 2,048자, `http://` 또는 `https://`로 시작. 빈 문자열이나 공백만 있으면 입력하지 않은 것으로 봄                    |
| descriptionMd       | 선택 | 선택 | 최대 100,000자 (공백을 자르지 않음)                                                                                    |
| serviceStatus       | 없음 | 필수 | 등록 시에는 서버가 정함. 수정 시 deploymentUrl이 없으면 `CLOSED`만 가능, 어기면 400이고 `field`는 `serviceStatusValid` |
| techTagIds          | 필수 | 필수 | 1개 이상, null 요소 불가                                                                                               |
| memberHandles       | 필수 | 필수 | 1개 이상. 각 항목의 앞뒤 공백을 자르고, 공백만 있는 항목은 불가. 등록자 본인을 넣어도 됨                               |

#### GitHub URL 정규식

```
^https://(?:www\.)?github\.com/([A-Za-z0-9._-]+)/([A-Za-z0-9._-]+?)(?:\.git)?/?$
```

- 통과: `https://github.com/owner/repo`, 뒤에 `.git`이나 `/`가 붙은 주소
- 실패: `http://`로 시작하는 주소, 레포가 빠진 `github.com/owner`, `/tree/main`처럼 경로가 더 붙은 주소

#### 프로젝트 주소(slug) 만드는 규칙

등록할 때만 만들고, 수정해도 바뀌지 않습니다.

소문자로 바꾸기 → 영문자·숫자가 아닌 문자가 이어진 구간을 하이픈 하나로 → 앞 연도(`2026-`) 떼기 → 앞뒤 하이픈 떼기

| 레포 이름     | slug                                  |
| ------------- | ------------------------------------- |
| `2026-loop`   | `loop`                                |
| `my_app`      | `my-app`                              |
| `2026_foo.js` | `foo-js`                              |
| `___`         | 만들 수 없음 → `PROJECT_INVALID_SLUG` |

`my_app`과 `my-app`, `2025-loop`와 `2026-loop`처럼 서로 다른 레포도 같은 slug가 될 수 있고, 이때는 `PROJECT_DUPLICATE_SLUG`입니다.

#### 그 밖의 규칙

- 등록은 크루·코치만 할 수 있습니다. 아니면 403 `PROJECT_REGISTRATION_FORBIDDEN`.
- 수정은 작성자만 할 수 있습니다. 작성자가 아니면 404 `PROJECT_NOT_FOUND`로 응답합니다.
- 팀원은 보낸 `memberHandles` 그대로 저장합니다. 등록자를 자동으로 넣지 않습니다.

### 프론트에서 맞춰야 할 것

#### 1. 글자 수는 코드포인트 기준

서버는 유니코드 코드포인트 기준으로 글자 수를 셉니다. JS의 `str.length`는 UTF-16 단위라 이모지 대부분을 2자로 세서, 서버에서는 통과할 입력을 프론트에서 막게 됩니다. `[...str].length`로 세면 서버와 같아집니다. 국기나 피부색이 들어간 이모지처럼 여러 코드포인트로 된 이모지는 양쪽 모두 2자 이상으로 셉니다.

#### 2. 서비스 검증 에러에는 필드 정보가 없음

형식 검증 에러(`VALIDATION_FAILED`)는 `details`에 필드명이 옵니다. `serviceStatusValid`는 서비스 상태 입력칸에 연결해 주세요.

아래 에러는 `details` 없이 코드만 오니, 코드를 보고 표시할 입력칸을 정해 주세요.

| 에러 코드                                                                       | 입력칸                                                                     |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `INVALID_COHORT`                                                                | 기수                                                                       |
| `PROJECT_DUPLICATE_GITHUB_REPOSITORY`                                           | GitHub URL                                                                 |
| `PROJECT_DUPLICATE_SLUG`                                                        | GitHub URL (레포 이름이 같거나, 앞 연도나 특수문자만 다른 프로젝트가 있음) |
| `PROJECT_INVALID_SLUG`                                                          | GitHub URL (레포 이름에 영문자나 숫자가 없음. 거의 발생하지 않음)          |
| `PROJECT_DUPLICATE_TECH_TAG`, `PROJECT_INVALID_TECH_TAG`                        | 기술 스택                                                                  |
| `PROJECT_INVALID_MEMBER`, `PROJECT_DUPLICATE_MEMBER`, `PROJECT_MEMBER_REQUIRED` | 팀원                                                                       |
| `PROJECT_INVALID_THUMBNAIL`, `PROJECT_THUMBNAIL_NOT_READY`                      | 썸네일                                                                     |
| `PROJECT_INVALID_DESCRIPTION_MEDIA`, `PROJECT_DESCRIPTION_MEDIA_NOT_READY`      | 본문                                                                       |
| `PROJECT_REGISTRATION_FORBIDDEN` (403)                                          | 입력칸이 아닌 권한 문제                                                    |

#### 3. 에러 예시는 Swagger에 있음

프로젝트 등록·수정 API의 400 응답에 제약별 예시가 있습니다. 글자 수 초과, 공백만 있는 값, GitHub URL 형식, 배포 URL 형식, 공백 handle, slug 불가, `serviceStatusValid`의 실제 응답 모양을 확인할 수 있습니다.
