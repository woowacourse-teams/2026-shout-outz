# 테스트 전략

## 목표

- 구현과 강하게 결합된 테스트를 과도하게 작성하지 않는다.
- 단순 테스크 커버리지를 높이는 것을 목표로 하지 않는다.
- 기능의 중요도와 위험에 따라 적절한 테스트 수준을 선택한다.

## 테스트 범위와 도구

테스트 범위와 도구는 아래 세부 항목을 참고한다.

### 1. 유틸리티 테스트

다른 환경에 의존하지 않는 함수는 가장 작은 단위에서 테스트한다.

대상 예시:

- 데이터 변환
- 문자열 처리
- 조건 계산
- URL 및 경로 생성

#### 테스트 러너

**Jest**와 **Vitest** 중 하나를 사용한다. 결정되는 경우 문서를 업데이트한다.

### 2. 컴포넌트·기능 테스트

React 컴포넌트와 기능 테스트에는 **React Testing Library**를 사용한다.

#### Test Harness

Router, QueryClient, Context 등 반복적으로 필요한 테스트 환경은 **Test Harness**로 표준화한다.

```tsx
renderWithProviders(<ProjectPage />, {
  route: '/projects/1',
});
```

Test Harness는 필요한 Provider를 일관되게 구성한다.

```text
renderWithProviders
│
├─ Router
├─ QueryClient
├─ Context
└─ Component
```

QueryClient는 테스트마다 새 인스턴스를 생성하여 이전 테스트의 캐시가 다른 테스트에 영향을 주지 않도록 한다.

#### 사용자에게 관찰되는 동작을 테스트한다

내부 state나 특정 함수 호출 여부보다 사용자가 실제로 관찰할 수 있는 결과와 행동을 검증한다.

```tsx
render(<Counter />);

await user.click(
  screen.getByRole('button', {
    name: '증가',
  }),
);

expect(screen.getByText('1')).toBeInTheDocument();
```

내부 구현을 변경하더라도 사용자에게 보이는 동작이 유지되면 테스트도 유지될 수 있도록 작성한다.

#### 요소 선택 기준

사용자가 화면을 인식하는 방식과 가까운 쿼리를 우선한다.

1. `role`
2. `text` / `label`
3. 의미에 맞는 접근성 속성
4. `test id`

가능하면 `getByRole`, `getByLabelText` 등 접근 가능한 정보를 사용한다.

테스트만을 위해 `data-testid`를 추가하는 것은 지양하며, 가능한 의미에 맞는 접근성 속성을 추가해 해결하도록 한다.

### 3. 네트워크 테스트

서버와 통신하는 컴포넌트 테스트에는 **MSW**를 사용한다.

네트워크가 포함된 컴포넌트 테스트에서는 **구현 함수 자체를 mocking하기보다 MSW로 API 경계를 mocking하는 방식을 기본으로 사용한다.**

다음과 같은 상황을 테스트한다.

- 정상 응답
- 빈 데이터
- 서버 오류
- 응답 상태에 따른 UI 변화

### 4. E2E 테스트

실제 브라우저 환경이 필요한 핵심 사용자 흐름에는 **Playwright**를 사용한다.

대상 예시:

- 로그인
- 인증 이후 페이지 이동
- 애플리케이션 진입 자체를 검증해야 하는 주요 시나리오
- 여러 페이지와 브라우저 상태가 연결되는 핵심 흐름

나머지 기능은 가능한 한 **React Testing Library** 수준에서 검증한다.

E2E 테스트는 실행 비용과 유지 비용이 크므로 핵심 사용자 흐름에만 제한한다.

### SSG 환경 검증

Playwright는 개발 서버가 아니라 **실제 SSG 빌드 산출물을 정적 서버에서 제공한 환경**을 대상으로 실행한다.

```text
소스 코드
   │
   ▼
SSG Build
   │
   ▼
dist
   │
   ▼
Static Server
   │
   ▼
Playwright
```

이를 통해 다음과 같은 배포 환경 문제까지 검증한다.

- 정적 페이지 생성 누락
- 에셋 경로 문제
- 클라이언트 초기화 문제
- 실제 정적 파일 제공 환경에서만 발생하는 문제

## 테스트 작성 원칙

### 사용자가 관찰할 수 있는 결과를 우선한다

내부 함수 호출 횟수나 state 값보다 화면에 나타나는 결과와 사용자가 수행할 수 있는 행동을 검증한다.

### 테스트를 위해 프로덕션 코드를 변경하지 않는다

테스트만을 위한 API나 DOM 구조를 추가하는 것을 지양한다.

요소 선택이 어렵다면 먼저 실제 마크업의 접근성과 컴포넌트 인터페이스를 개선할 수 있는지 검토한다.

### 커버리지 수치를 목표로 삼지 않는다

커버리지 자체를 목표 수치로 관리하지 않는다.

단순 마크업이나 props 전달처럼 회귀 위험이 낮은 부분까지 테스트하기보다 **기능의 중요도와 실제 회귀 위험을 기준으로 테스트 필요성을 판단한다.**

## 실행 시점

자동화된 테스트는 PR 워크플로우에 포함한다.

PR이 생성되거나 변경될 때 테스트를 실행하고, 테스트가 실패한 상태에서는 merge하지 않는다.

실제 실행 명령은 `package.json`의 scripts를 기준으로 한다.

기본적인 유틸리티 테스트와 React Testing Library 테스트는 빠르게 실행하여 대부분의 회귀를 먼저 발견한다.

Playwright E2E는 소수의 핵심 시나리오만 유지하며, 실제 SSG 빌드 산출물을 대상으로 실행한다.
